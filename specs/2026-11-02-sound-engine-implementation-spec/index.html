    2. Architecture#

    2.1 Layers#

    2.2 Data flow#

    1. Request: audio.sound(source, pitch=..., notes=..., chord=..., length=..., transpose=..., parameters=...).
    2. Strings are resolved per feature spec §3.2. A short name goes through the SOUND_DIRECTORY index, which is built on the first short-name lookup by reading only the table names of each .toml file. A path goes to that file's [sounds.<name>], or to the recorded file.
    3. Each sound file is parsed and validated once, when first touched, into frozen models.
    4. The source and identity arguments resolve to an immutable SoundSpec: the instrument, concrete Hz pitches, note events in seconds, fixed parameter values, seeds, tuning, and whether it is live.
    5. The identity key is the SHA-256 of the spec's canonical JSON (§6.2).
    6. Cache lookup: the key is looked up in the memory cache (then the disk cache, from M3). A hit returns the existing Sound object, so equal requests return the same object (AUD-FUNC-002).
    7. Compile (on a miss):
    8. Baked: render a float64 buffer and check it is finite. Report its peak; clip and warn if it is above full scale, or scale it to -1 dBFS if normalize. Convert to int16 at the mixer rate with synth.to_pcm16 [Fact], and make a pygame.mixer.Sound from it when a mixer exists.
    9. Live: build wave tables and filter coefficients; no audio.
    10. Recorded file: load it with pygame.mixer.Sound(path) (no mixer: decode it with the wave module for offline use, WAV only).
    11. In every case the time is recorded with clock.raw_counter_seconds [Fact], attributed to "setup" (before the scene's first logic frame) or to the current frame number.
    12. Play: sound.play(...) allocates a channel (§7.1), calls Channel.play(sound, loops) and then Channel.set_volume(left, right). The mixer (C, SDL's audio thread) does the rest.
    13. Live: sound.start(...) creates a LiveVoice on a reserved live channel. Each frame, AudioEngine.update renders the next chunk when the queue has room (today's mechanism [Fact]), reading the latest coalesced parameter values.
    14. Offline: OfflineMixer takes compiled float buffers (or steps live renderers with a parameter timeline) and sums them at exact sample offsets into a file.

    There is no second clock and no second output device. The mixer is the only device owner [Proposal; decisions D3/D4].

    3. Backend decision (D3) and evidence#

    3.1 Options considered#

    Option Description Verdict
    A. pygame.mixer + compiled (baked) sounds + main-loop live chunks Extend what exists. Baked sounds mix in SDL's C mixer; live voices render on the main thread in chunks Recommended
    B. A Python render callback on a device thread (pygame._sdl2.audio.AudioDevice(callback=...) or miniaudio.PlaybackDevice with a generator) The classic "audio callback" architecture, with DSP in numpy on the audio thread Rejected: measured to miss deadlines under GIL contention (A.2)
    C. A Python render-ahead worker thread + copy-only device callback Render blocks on a worker thread into a ring buffer; the callback only copies Rejected for M1–M5: needs about 85 ms of lookahead to survive a busy game loop (A.3), no better than A's 100 ms chunks, while adding a second device and threads
    D. A native DSP core (C via cffi, or Rust) owning its own callback without the GIL The only route to low-latency, sample-accurate real-time mixing, real-time bus effects and a master limiter Deferred to an M6 gate [Open]: adds native builds for every platform plus a separate WebAssembly build, for features not yet asked for
    E. Free-threaded CPython (3.14t) running B or C without the GIL Removes the contention that sinks B and C Deferred [Open]: pygame-ce, numpy and the engine would all need free-threaded builds and audits

    3.2 Why A#

    • [Owner] "the first time you call for a sound, it gets compiled ... the way you load it is the same as the way you'd use it in the game - one API." Option A compiles on request and plays compiled audio from memory, which is exactly that model.
    • A Python callback cannot reliably meet a 5.33 ms (256-frame) deadline while the game loop runs Python. [Measured A.2] With a pure-Python busy main thread, a numpy render in a miniaudio callback took 256 ms (p99) at the default 5 ms switch interval, 58 ms at 1 ms and 12.7 ms at 0.2 ms.
    • The same numpy render is cheap when uncontended [Measured A.1]: 64 voices of oscillator + envelope + pan take 0.40 ms (p99 0.47 ms) per 256 frames. On the main thread there is no contention.
    • Today's main-thread costs are small [Measured A.4]: a 100 ms live chunk with a low-pass takes 0.15 ms, and the worst existing recipe takes 9.7 ms, compiled once.
    • One device means no competing mixer, no second clock, and nothing new for the replay silencer, headless runs or the browser to learn.
    • There are no new dependencies (AUD-PORT-001).

    3.3 What A gives up (recorded honestly)#

    • Trigger latency: play() starts at the next mixer buffer, about ≤ 11.6 ms after the frame that called it. It is not sample-accurate.
    • Live-parameter latency: up to one chunk (100 ms today; M3 evaluates 50 ms) plus one buffer.
    • Real-time bus effects and a master limiter are not possible, because SDL's mixer sums in C with saturation. Effects are compiled into sounds instead.
    • Sample-accurate transitions between music pieces are not possible. Inside a compiled sound, timing is sample-accurate.
    • Pitch at play time cannot change a compiled sound, because pygame plays at a fixed rate. Each pitch is its own sound, requested by identity.

    3.4 The native-core gate (M6) [Open]#

    Option D is reopened only if the owner asks for one of:

    • real-time bus effects (a reverb send, a master limiter);
    • sample-accurate music transitions;
    • more than 8 simultaneous live voices;
    • trigger latency under 10 ms.

    The experiment would be a C core built with cffi (the toolchain pyminiaudio already uses [Fact]) for macOS arm64/x86_64, Linux and Windows, plus an Emscripten build, measured with the Appendix A harness. If it fails, the fallback is A as specified. The Renderer layer is pure functions over SoundSpecs, so a native core would replace only the Output and Live layers.

    4. Execution model#

    4.1 Threads#

    Thread Runs Owner
    Main (game loop) all API calls, compiles, live chunk rendering, channel allocation, bus volume updates, diagnostics engine
    SDL audio thread pygame's C mixer: sums playing channels, and calls the channel-finished callback that queues a live voice's next chunk [Fact] SDL

    No new thread is created [Proposal]. The brief's command-queue and memory-ordering requirements apply only to the deferred native core (§3.4). With one thread there is nothing to queue: an API call takes effect through pygame's own thread-safe mixer calls.

    4.2 Bounded work per frame#

    AudioEngine.update(dt=...) runs once per frame, in the slot where LiveAudio.update runs today [Fact: scene.py:1227], with the same scene and pause arguments. It:

    1. advances scheduled plays whose frame has arrived (M2; feature spec §7.1, late rule);
    2. advances each unpaused voice's played time by dt and reaps voices whose sound has ended (§7.3);
    3. for each live voice whose queue has room, renders one chunk with the latest parameter values;
    4. applies bus fades and ducking (one gain step per bus per frame; M5);
    5. records diagnostics: counters and clock.raw_counter_seconds deltas, kept in fixed-size ring arrays.

    The work is bounded: at most live_pool chunks, at most one reap per channel and one operation per bus. The only compiles in a frame are the ones the game requested in it. They are timed, counted and listed with their frame (AUD-FUNC-003).

    4.3 Parameter updates (coalescing)#

    LiveSoundHandle.set(name, value) writes latest[name] = clamp(value) into a small dict owned by the voice, and rendering reads the dict once per chunk. A thousand calls per frame cost a thousand dict writes and render nothing extra (AUD-GAME-003). Smoothing runs inside the chunk as a one-pole glide from the previous chunk's end value toward the new target, with time constant smoothing_ms, in closed form per sample: target + (start − target)·exp(−n/τ).

    4.4 Handles and stale-handle protection#

    @dataclass(frozen=True, slots=True)
class SoundHandle:
    slot: int          # index into the voice table
    generation: int    # the slot's generation when this handle was issued

    Each voice-table slot has a generation counter, incremented whenever the slot is reused. Every handle method first checks table[slot].generation == handle.generation. On a mismatch it does nothing and returns False. Handles hold no reference to the Sound, so a dropped handle releases nothing, and a kept one keeps nothing alive.

    4.5 Resource release#

    pygame.mixer.Sound objects are released when the library drops them. That happens only through LRU eviction (memory limit) or engine shutdown. Eviction never removes a sound that is playing, because the voice table holds a reference while the voice plays. Compiled sounds outlive scenes: a second scene requesting 'coin' gets the same compiled sound.

    Denormals and non-finite values: every stateful recursion flushes values with a magnitude below 1e-30 to zero at chunk boundaries. Every compiled buffer and live chunk is checked with np.isfinite. A compile that fails the check raises SoundRenderError naming the sound (a bug, surfaced at the request). A live chunk that fails it is replaced by silence, the voice is released, and the event is counted (AUD-RT-004).

    Oversampling: only for compiled saw, square and pulse (PolyBLEP alone measured 26.8 dB at 3520 Hz, short of AUD-WAVE-006's 40), for drive above 2 and for FM with index > 4 (2×, compile-time only, so it is bounded by the sound's length). Live voices (M2, draft tier) never oversample. Quality tiers: full (compiled: cubic interpolation and oversampling where listed) and draft (live: linear interpolation, no oversampling). Neither tier is described as hardware emulation.

    De-clicking without smoothing the waves [Call]: only boundaries get ramps, and only where needed:

    • A v1 sound whose first sample's magnitude is above 1/1024 gets a 1 ms fade-in. One whose last sample is above that gets a 2 ms fade-out. hard_edges = true turns both off, for intentional clicks.
    • Stops, steals and skips use Channel.fadeout (≥ 5 ms).
    • Live voices get rendered fades [Fact: today's _fade_gains].
    • Waveform edges inside a sound are never smoothed.
    • v0 recipes get none of this; they compile through today's renderer unchanged (§10.4).

    Level [Call]: compiled sounds keep the author's levels; there is no automatic normalization (feature spec §6.5). normalize = true scales to -1 dBFS. A peak above full scale is clipped and logged once.

    6.2 Identity and cache keys#

    The SoundSpec is serialized to canonical JSON: sorted keys, and floats written with repr, which round-trips exactly. The JSON also includes:

    • the mixer sample rate (44100 when no mixer is running);
    • the tuning;
    • AUDIO_RENDER_VERSION, an integer bumped whenever the renderer's output changes;
    • the numpy version;
    • the platform tag.

    The key is the first 128 bits of the SHA-256 of that JSON. Any change to any of these is a miss (AUD-ASSET-006). A cheaper first-level lookup avoids re-resolving on every call: the library memoizes (source string or Instrument id, frozen identity arguments) → key. That makes a repeated audio.sound('coin') a dict hit.

    6.3 Seeds#

    Each source's seed is the instrument's seed if given; otherwise it is derived from the sound's name with int.from_bytes(sha256(sound name)[:8]). Either way it is combined with the source's index through numpy.random.SeedSequence. Compiles never touch glitchygames.randomness streams, which respects both the CRT power-on's "no randomness" rule and replays [Fact: the power-on rules in crt_power_on.py]. Version 0 recipes are the exception (§10.4).

    6.4 The cache: None, 'ram' or 'disk' [Owner]#

    AudioEngine(cache=...) takes the --sound-cache option, which is replay-local (§10.2):

    • None: sound() resolves and validates, but keeps no audio. The returned Sound holds only its spec, and every play() compiles it in that frame. The compile is timed and accounted like any other (§11.0). This is the switch that forces mid-frame rendering.
    • 'ram' and 'disk': as below.

    Today's code does not read the mode. It is migrated and removed first (M2, §10.4), and the benchmarks then run in the owner's order: None, then 'ram', then 'disk' (M3, §11.0) [Owner]. None and 'ram' exist from M1, so every test of the new engine can run under both.

    • Memory ('ram'): a dict[key, Sound] plus an LRU order on last play. Total int16 bytes are tracked. Above --sound-cache-memory (default 256 MB), the least recently played sounds that are not playing are dropped. They are recompiled on their next request, which is counted.
    • Disk ('disk', M3): memory first, then disk.
    • Layout: <cache>/sounds/<render_version>/<key[:2]>/<key>.wav (16-bit PCM WAV at the mixer rate), written with output_files.write_aside_then_replace [Fact].
    • The cache root is a new state/paths.get_cache_directory(app_name) beside get_save_directory [Fact]: macOS ~/Library/Caches/<app>/, Linux $XDG_CACHE_HOME/<app>/ (default ~/.cache/<app>/), Windows %LOCALAPPDATA%\<app>\Cache\.
    • The size limit is 64 MB, and the oldest-accessed files are pruned at startup.
    • Reads verify the WAV header's rate and length. A bad file is deleted and recompiled.
    • In the browser and in tests, 'disk' falls back to 'ram' with one log line. Under --headless outside tests it is honoured, so the M2 startup benchmark can measure it.
    • [Call] The disk layer persists across runs and the engine prunes it, rather than using per-run temp files, because the identity hash makes re-use safe and that is what lets a second launch skip compiling.

    6.5 Where compiles happen#

    There is one rule: the first request with a given identity compiles. The places it happens are conventions, not separate APIs.

    1. Setup (the convention): games call audio.sound(...) in setup(). Those compiles run before the scene's first logic frame and are attributed to setup. A setup whose compiles exceed 50 ms logs one INFO line naming the slowest sounds.
    2. Loading screens: audio.sounds.warm(requests, budget_ms=...) takes a list of sound(...) argument sets and compiles as many as fit in the budget each time it is called, returning progress from 0 to 1. It exists only so a loading scene can spread work across frames; it calls the same compile path.
    3. Gameplay: a first request inside a gameplay frame compiles there. It is timed, counted and listed with its frame (AUD-FUNC-003).
    4. The engine's own sounds (CRT) compile before the power-on, in GameEngine._power_on_sound_cues, which _run_game (the blocking start) and start_async (the browser's) call when the power-on plays (§10.1); only the process's first power-on compiles them, every later one reuses them (§10.1, compiled once per process).
    5. Recompiles: after eviction, a tuning change or (M4) a hot reload, the next request compiles again and is counted.

    6.6 Hot reload (M4)#

    With --sound-hot-reload, the library records each sound file's mtime. At most once per second, measured with clock.elapsed_seconds [Fact], AudioEngine.update checks them. Hot reload is refused with --record-trace and --replay-trace (OPTIONS_REFUSED), so it never touches a replay. For each changed file:

    1. the file is re-parsed and the short-name index refreshed;
    2. memo entries that came from it are dropped, so the next request resolves again and compiles if its identity changed;
    3. playing voices finish the old audio.

    7. Voices, buses and the mixer#

    7.1 Channel table and the legacy partition#

    At engine start, where the live pool is reserved today [Fact: game_engine.py:1817]:

    set_num_channels(live_pool + library_channels + legacy_channels)   # default 4 + 32 + 8
set_reserved(live_pool + library_channels)                         # 0 .. 35 reserved
    Channels Used by How chosen
    0 .. live_pool-1 live voices (today's pool, unchanged [Fact]) LiveAudio
    live_pool .. live_pool+library-1 the sound library the library's own table (Channel(i).play)
    the rest (8, pygame's default count) legacy Sound.play() callers: SoundBank, load_sound, any game code SDL picks among unreserved channels

    The library never calls Sound.play(), and legacy callers can never reach reserved channels, so neither cuts the other off (AUD-MIX-008). The one-time reservation keeps today's rule that the pool is never resized [Fact: BUGS.md #145; reserve_live_voice_pool already handles a second engine in one process].

    Allocation for a library play on bus b with priority p:

    1. Take a channel that is free in the table. Whether a channel is free, and so whether a play steals, is decided by the table alone, so it is the same in a replay: a channel is free when its voice ended by played time (§7.3), or a stop's fade has run out in frame time. The device check (Channel.get_busy()) only chooses among the free channels: the lowest-numbered one not busy on the device, else the lowest-numbered free one anyway, accepting a cut tail of at most one device buffer. It never changes what the game sees (§7.3). A free channel counts against b's reservation if b is under its reservation. Otherwise only channels not needed by other buses' unmet reservations are eligible.
    2. Otherwise steal: among playing voices with priority ≤ p, choose by releasing first, then lowest priority, earliest start, lowest channel. Fade it with Channel.fadeout(10) and mark its channel fading. The new sound starts this frame on another free or fading-complete channel if one exists. Otherwise it starts on the stolen channel next frame, counted as a one-frame delayed play. [Measured] (M1, 2026-11-02, tests/benchmarks/test_channel_fade_relations.py, run under --benchmark-only because it depends on the mixer thread's timing, and tests/audio/test_channel_fades.py on SDL's disk driver; pygame-ce 2.5.8, SDL 2.32.10, SDL_mixer 2.8.2): Channel.play straight after Channel.fadeout(10) on the same channel replaces the fading sound at the next mixer chunk, so the fade is never heard (worst step 10.3 times a 440 Hz tone's own largest, over six steals), and the delay is kept. [Open] The delay does not make a steal smooth either: SDL_mixer sets a fading channel's volume once per chunk (512 frames, 11.6 ms), so a 10 ms fade is one plateau or an immediate halt (worst step 8.3 to 9.7 times the tone's own in two recordings of six steals). A smooth steal needs a fade of several chunks or an engine-rendered fade tail (risks R4 and R5); the owner decides.
    3. Otherwise drop and count.

    Which voice is stolen is decided from the table alone, so it is deterministic (AUD-MIX-003). Which channel index a play lands on may vary with device timing; that is not visible to the game.

    7.2 Volume and pan#

    Channel.set_volume(left, right) is called after Channel.play, because pygame resets channel volume on play [Fact: noted in replay/silence.py]. The gains are:

    • left = v·g_bus·g_master·cos(θ)
    • right = v·g_bus·g_master·sin(θ)
    • with θ = (pan + 1)·π/4, a constant-power law at -3 dB centre.

    Bus changes re-apply to every playing channel of that bus. A bus fade is applied as one set_volume per frame (60 steps/s). [Measured] (M1, 2026-11-02, tests/audio/test_channel_fades.py on SDL's disk driver): each frame's gain reaches the channel whole at the next mixer chunk, so a 50 ms fade from full to silence is three steps of a third (levels 1, ⅔, ⅓, 0, each held for one or two chunks), with a worst step 5.2 to 5.3 times a 440 Hz tone's own largest. [Open] Whether those steps are heard as zipper noise for the gain ranges involved is the owner's listening check; the fallback is to render the fade into a short tail sound. Voice stops, steals and skips use Channel.fadeout, which SDL_mixer also steps once per chunk rather than ramping (§7.1, §10.1), so a fade shorter than a few chunks is a plateau or two and a halt.

    7.3 Voice time without asking the device (fixes the builder check's first finding)#

    Each voice keeps played_seconds. AudioEngine.update(dt=...) adds the frame's served dt (the recorded dt in a replay [Fact]) only while the voice is not paused:

    • Ending: a baked voice ends when played_seconds ≥ length. A looping voice ends only when stopped (or released, at the end of its pass). A stopped, cancelled or stolen voice ends at once: its handle reports is_playing False immediately, while its channel stays fading for allocation until the fade has run out in frame time.
    • Pause: pausing (a pause screen over the owner scene, a playback scope [Fact: today's paused_owners]) calls Channel.pause() and stops advancing played_seconds. Resuming calls Channel.unpause(). A paused voice is never reaped, and its channel is never reused while it is held.
    • What the game sees: handle.is_playing and reaping use only played_seconds, never Channel.get_busy(). A game reading is_playing therefore gets the same answer in a replay (replay/silence.py warns that device-busy answers are not replay-safe [Fact]).
    • Silenced frames: FrameSilencer stops channels [Fact]. It also calls audio.silenced(channel) (one new call), which marks the channel's slot device-stopped and nothing more: the voice keeps its generation and its played_seconds, so is_playing, its end and later steal decisions follow frame time exactly as in the run that was not silenced. Only the channel is quiet; the table reuses it as usual. A rebuild's and a fast-forward's frames are compared with the recording, so a silenced frame must not change what the game sees.
    • Before frame 0: voices started by the engine itself (the CRT) belong to the engine's system owner, not a scene. During the power-on, the power-on's frame loop calls audio.update(dt=frame_seconds) with its own measured frame time. Those voices are never game-visible, so measured time is acceptable for them. After the power-on they persist into the first scene (§10.1).

    7.4 Buses#

    The buses are a tree of Bus(name, parent, volume, mute, solo, reserved_channels, loudness_budget):

    • The effective gain is the product of the volumes along the path.
    • Solo mutes the subtrees of non-soloed siblings.
    • duck_under (M5) registers a rule. Each frame, if the trigger bus has a playing voice, the ducked bus's gain moves toward 10^(amount_db/20) at the attack rate. Otherwise it moves back at the release rate.
    • Loudness budget (M2): the sum over a bus's playing voices of peak × channel gain. When it is above the budget, the bus gain is multiplied by budget/sum, with a 30 ms recovery. This is an estimate from compiled peaks and never reads audio back.

    7.5 Live voices (M2)#

    The existing LiveVoice/LiveAudio [Fact] is generalized. A LiveVoice renders chunks from a compiled live instrument (sources, routes, filter state, smoothed parameters) instead of a single waveform with a cutoff:

    • The chunk length is configurable with --live-chunk-ms (default 100). M3 measures 50 ms against the underrun probe (scripts/audio_glitch_probe.py [Fact]). The safety margin is the chunk minus the device buffer [Fact: module docstring], so 50 ms leaves about 38 ms.
    • The pool grows from 4 to 8 only if AUD-RT-002 holds on the CI Linux container profile (1 CPU [Fact: nox -s test-linux-ci]).
    • scene_manager.live_audio.create_voice(...) stays, implemented on the new voice table.

    7.6 Streams (M5)#

    audio.music.play_file wraps pygame.mixer.music: one stream, decoded by SDL_mixer. Its volume follows the music bus. FrameSilencer already follows mixer.music.pause/unpause [Fact].

    9. Determinism and offline rendering#

    • Scope (D8): bit-identical output for a fixed AUDIO_RENDER_VERSION, Python, numpy, platform tag, sample rate, configuration, asset set, seeds and parameter timeline. Across platforms, comparisons use a tolerance of max |Δ| ≤ 2⁻¹⁴ (about −84 dBFS) on float buffers before int16 conversion, because numpy's sin/exp may differ in the last ULPs.
    • Offline mixer:
    • It sums the float buffers of compiled sounds at round(event_seconds × rate), applying the same volume and pan law as §7.2, with bus stems if asked.
    • Live sounds are rendered offline by stepping their chunk renderer through a scripted parameter timeline. That is the same code as the device path, with the same chunking.
    • Parity: device-path parity is tested on the pre-device buffers. The buffer that feeds pygame.mixer.Sound must equal, bit for bit, the buffer OfflineMixer uses for a single event at offset 0. The device's own mixing (SDL, int16 saturation) is out of scope.
    • Tail termination: rendering stops when the output stays under −90 dBFS for 100 ms after the last event's nominal end, or at tail_seconds. The stop is reported in RenderReport with the peak and the clip count.
    • Recording soundtracks (M5, feature spec §13.3):
    • Each frame logs its plays (audio_events: sound identity, playback arguments) as a measurement field. It is never compared or served, like processing_seconds [Fact].
    • glitchygames sound render-recording run.jsonl.gz mixes them offline.

    10.1 CRT power-on sound (M1)#

    • The sounds: a new leaf module, src/glitchygames/crt_power_on_sound.py, holds the CRT instruments and their tunable named constants (FLYBACK_WHINE_HZ, DEGAUSS_HUM_HZ = 60.0, BARS_TONE_HZ = 1000.0, STATIC_SEED). It requests them through audio.engine_sound(Instrument(...), pitch=..., length=...), the engine's own sounds' sound (SoundLibrary.engine_sound): the same identity, compile path and accounting as games' audio.sound, with one cache of its own.
    • Compiled once per process [Owner] (2026-11-02: "it'll be used at least once, but possibly multiple times, if we're playing in the arcade"): the CRT's compiled samples are kept in a process-wide cache owned by the engine (glitchygames.audio.library.ENGINE_SOUND_CACHE), keyed by each sound's identity key (§6.2: it holds the mixer's rate and the tuning, so a mixer restarted at another rate compiles anew and never reuses a wrong-rate sound). Every later power-on in the process reuses them: a second game run in one process (the Arcade, the test harness's repeated engines) and every engine context compiles nothing for the CRT.
    • Scope: only the engine's own CRT sounds. Game sounds stay per engine context in each context's SoundLibrary, and each context keeps its own AudioEngine, voices and accounting.
    • What is shared: the compiled samples (float64 and int16, made read-only) with their peak and rate, never a Sound: each library makes its own Sound over them, because a Sound carries its context's player (attach_player, the engine whose voices play it) and its own pygame sound, built from the samples on its first play. A pygame Sound could be played from several channels at once, but sharing one would tie every context to the mixer it was built on; building one per context is a copy of the samples, not a compile. The cache is a read-only cache in the engine context's sense (plans/2026-10-25-engine-context.md: values computed only from their keys, never written after they are made).
    • Cache mode and memory limit: the cache is exempt from both. Under --sound-cache none the CRT's sounds stay compiled and their plays compile nothing (none is a game's benchmark switch; the CRT is engine-owned); the memory limit never evicts them, and bytes_held leaves them out.
    • Accounting: the first compile is counted and attributed like any compile, in the context that triggered it (a miss, a setup compile, in its compile log); every reuse is a counted cache hit.
    • Lazy: they compile on the first power-on that plays its sound, so headless runs, tests that never power on and --crt-power-on-sound off pay nothing. Tests start with an empty cache (tests/harness.py empty_engine_sound_cache).
    • The cue hook: crt_power_on.play_power_on and play_power_on_async get one new keyword argument, sound_cues: PowerOnSoundCues | None = None. It is a small protocol:
    • at_progress(progress), called every power-on frame with the same progress value that drives the picture (§12.1 cues are progress fractions); each cue starts on the frame nearest its point, the next frame's progress predicted from the last step (ruling R42), so at a steady frame rate a sound is at most half a frame off;
    • skip(), which fades every CRT voice with Channel.fadeout(20). [Open] (AUD-CRT-003, ruling R41): SDL_mixer 2.8 recomputes a fading channel's volume once per mixing callback (mix_channels in src/mixer.c, from SDL_GetTicks) and applies it to the whole chunk (512 frames, about 11.6 ms), so the 20 ms fade is a plateau or two and then a halt, not a ramp. The voices end within 20 ms plus one chunk; the step on a pure tone is measured against the model in tests/test_crt_power_on_sound.py (a strict xfail holds the "no step above threshold" criterion). [Measured] (M1, 2026-11-02, tests/audio/test_channel_fades.py on SDL's disk driver): the model holds on the device: Channel.fadeout(20) on a 1 kHz tone is one or two plateaus then a halt, every level change on a chunk boundary, with a worst step 4.5 to 4.9 times the tone's own largest (from 1.0 to 4.9 across twelve skips; the model's worst over eight phases is 3.4). The criterion stays unmet (strict xfails in both test files).     16. Summary#

    Recommended architecture:

    • pygame.mixer stays the only device owner.
    • One call, audio.sound(...), takes a short name, a path or an Instrument. The first request compiles the sound into memory, later requests return it from the engine-owned cache, and .play() plays it.
    • The surrounding API covers pitch types (notes, hertz, MIDI and scale steps side by side), named and blendable waves whose numbers are named, and TOML instruments.
    • Continuously controlled sounds render in live chunks on the main thread, extending today's LiveVoice.
    • There are no new dependencies and no new threads, and nothing new for replays, headless runs or the browser's compiled-sound path to learn.

    Demonstrated by experiment (Appendix A, throwaway):

    • a numpy renderer is fast when uncontended (64 voices at about 9% of a 256-frame budget);
    • the same renderer on an audio thread misses deadlines badly under GIL contention;
    • render-ahead on a worker needs about 85 ms of lookahead under a busy loop;
    • today's recipe and live-chunk costs are small.

    Still proposals:

    • every API shape and default, and the schema;
    • the cache and disk layout;
    • the DSP algorithm choices (from cited literature);
    • the stealing, fading and bus behaviours on pygame's channels (R4 and R5 need M1 checks);
    • all performance gates.

    Main risks: live-voice underruns on slow targets (R1), a future need for real-time effects that option A cannot meet (R2), and gameplay-time compiles (R3, made visible by diagnostics).

    Order of work [Owner]: API (M1), then migration and clean-up (M2), then measurement with the cache off, ram, then disk (M3), then the deeper features.

    First implementable milestone (M1): the pitch, wave and instrument API; audio.sound(...) with compile-on-first-request, short names and paths; notes and chords; buses and voice management with the legacy channel partition; offline render to WAV; the CRT power-on sound; the Sound Board demo; and the A/B benchmark that measures the smoothness claim.

    A.2 Python render in a device callback under GIL contention#

    A miniaudio.PlaybackDevice (float32, stereo, 48 kHz) rendered workload A in its generator on each callback. Meanwhile another thread ran pure-Python arithmetic continuously, a worst-case busy game loop.

    Switch interval Render time in callback, p99 Callback period p50
    5 ms (Python default) 256.6 ms 230 ms
    1 ms 58.4 ms 50 ms
    0.2 ms 12.7 ms 15 ms

    Each numpy call releases and reacquires the GIL, and every reacquisition waits behind the busy thread. Even at 0.2 ms the render takes more than twice the 5.33 ms budget. Conclusion: option B is rejected.

    A.3 Render-ahead worker + copy-only callback under the same contention#

    A worker thread rendered 256-frame blocks into a ring, and the miniaudio callback only copied bytes. The switch interval was 0.5 ms, the engine's own [Fact]. Each run lasted 5 seconds.
