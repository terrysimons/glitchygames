## Goal

Turn what recordings already hold into historical metrics, and use the frame budget the game
leaves unused (headroom) to run AI and GPU work for enhanced gameplay without missing frames.

## What recordings hold today

- **Header** `measurement_runs` (newest first, at most 10): machine, paced or not, pacing timer
  and measured sleep model, engine/pygame/Python versions, `measured_at`, `rebaselined_from`,
  hash scheme, frame count
- **Every frame:** `processing_seconds` and `content_hash` histories (index `i` = run `i`, at
  most 10), and its content: raw `dt`, event batches, input changes, control events, scene,
  every sprite's rect, visibility and draw order
- Only a `--rebaseline` stacks a run; replays and test runs measure and keep nothing

## Parts (all chosen by the user)

### Part 0: Run provenance (foundation for Parts 1, 2 and 5)

**Done (2026-10-23): the source revision.** `glitchygames/build_info.py` (user decision: git in
a checkout, `export-subst` for archives, a build stamp for packages; no stamp commits):
`MeasurementRun.source_revision` holds the commit, its date, uncommitted changes and how it is
known. **Done (2026-10-23): machine state.** `glitchygames/machine_state.py`:
`MeasurementRun.machine_state` (CPU model, logical CPUs, memory, mains or battery, macOS's
`pmset -g therm` report kept as reported, continuous integration), read once per process as its
first run starts (about 18 ms on macOS; every run cost the suite ~30 s). Still to do in Part 0: the per-run summary.

Each `MeasurementRun` also records the git commit and whether the tree had uncommitted changes
(absent outside a checkout), the CPU model, power source (AC or battery) and thermal state where
the platform reports them, and CI or local. Without these, "slower" is often a laptop on
battery, and a regression cannot be pinned to a commit. Read leniently, like the other fields.

Each run also carries a **summary** of its frames (user decision, 2026-10-23): total
processing time, p50, p95, p99, the worst frame (index, time and scene), frames over budget,
and the `dt` jitter, so tools and the ledger read trends from the header without scanning every
frame. Filled in when the run's recording closes (the header is written first, so the summary
is written where the format allows it: Open, settled in Part 0's sub-plan, e.g. a trailer line
or a rewrite on close, as `--rebaseline` already moves a finished file into place).

### Part 1: Frame performance history

Per recording, a frame × run table of `processing_seconds` (the 10 stacked runs), with the
content hash proving each run did the same work (a frame whose hash changed is shown as
"different work", never as a speed change). Reports: frames or spans that got slower or faster
between runs, by scene, with the run's commit (Part 0). Output: a text report from a script and
a heatmap on the docs site.

**Beyond 10 runs** (chosen by the user, 2026-10-23): a run ledger outside the recordings (one summary row per recording per run:
total, p50, p95, p99, worst frame and its scene, plus the run's provenance). `nox -s
replay-metrics` replays every golden replay and bundled demo headless with processing measured
and appends rows; CI runs it on every merge, so the history builds on one machine. Open: where
the ledger lives (a JSON Lines file on the gh-pages branch, which the docs build reads, is the
proposal; SQLite in a cache directory is the alternative).

### Part 2: Behaviour-change map

From the `content_hash` histories: for each pair of adjacent runs, the frames whose hash
changed, grouped into spans, with the first changed frame's scene and the runs' commits. "Run 4
changed behaviour from frame 812 (scene `Game`), commit abc1234". This is the first half of a
bisect: the commit range and the exact frame to look at.

### Part 3: Frame headroom, measured and used

**Measured (history):** headroom = frame budget (1 / target FPS) − processing time, per frame.
Per scene and machine: p50, p5 and worst headroom, and how often a frame overran its budget.
This says how much spare time each scene really has, on which machines.

**Used (runtime, the reason for this part):** the user's goal is to spend that spare time on AI
and GPU tasks for enhanced gameplay. Today the frame's slack is spent sleeping in the pacing
step (`SceneManager._finish_frame`). Proposal:
- The engine exposes this frame's remaining budget (the deadline minus now, minus a safety
  margin) and a forecast per scene from the history (e.g. its p5 headroom on this machine), so
  a game can size work before starting it
- A spare-time work queue: a game submits jobs (an AI decision, a model inference, a GPU
  shader pass, sound generation); the engine runs slices of them in the pacing step instead of
  sleeping, stopping at the safety margin, and runs blocking or long jobs on a worker (thread or
  child process) whose results arrive at a later frame
- **Determinism rule (non-negotiable):** a job's result reaches the game only through the doors,
  like device input: recorded when it is delivered, and in a replay served from the recording
  instead of being computed again. So a replay never depends on how fast the machine was, on
  the model's own nondeterminism, or on having the GPU or model at all
- Open: GPU access. pygame-ce has no GPU compute; candidates are Metal through MLX or PyTorch
  on macOS, CUDA or Vulkan elsewhere, or SDL 3's GPU API once pygame-ce exposes it. The queue
  is backend-neutral; the first job type can be CPU-only AI
- Open: the margin policy (fixed, e.g. 1 ms, or learned from this machine's history)

### Part 4: Pacing steadiness

From each frame's recorded `dt` against the target frame time: jitter, late-frame rate and
the worst stalls, per machine and pacing timer (the run records which). A historical version of
`nox -s timer-report`, measured in real play rather than a probe.

### Part 5: Machine comparison

The same recording's frames measured on different machines give a speed ratio per machine
(median of per-frame ratios over frames with equal content hashes), so processing times can be
normalised before they are compared, and Part 3's forecasts can be carried to a machine that
has no history yet.

### Part 6: Gameplay analytics

From the recorded content: player position heatmaps, where the player is caught or dies, time
to clear each level, inputs per minute, pause frequency and idle time. Games may also record
stat events (a supervisor action, such as `caught`, `level_cleared`, `muncher_eaten`) so
analytics need not reverse-engineer sprite positions; the format carries them already
(control events). First use: Mr. Muncher's difficulty tuning from the user's own recorded play.

Stat events are chosen (user decision, 2026-10-23): a game records them with one call (a thin
wrapper over `record_control_event`, kind `stat`), replays carry them, and analytics read them
first, falling back to sprite positions only for what no event names.

### Part 7: Richer per-frame measurements (all chosen by the user, 2026-10-23)

New measurement fields (listed in `MEASUREMENT_FRAME_FIELDS`: never hashed, never compared,
never served), each with its own newest-first history like `processing_seconds`:
- **Step timings:** the frame's time split by loop step (logic `dt_tick`, event processing,
  frame services, camera aim and positioning, render `update()` + draw, present), so "slower"
  becomes "rendering got slower"
- **Pauses that are not the game's fault:** garbage collection pauses (`gc.callbacks`: start and
  stop per collection, generation, objects collected) and the process's memory (RSS every N
  frames, plus the frame's allocation count delta where cheap), which explain most stray spikes
- **Drawing cost:** sprites drawn, dirty rectangles and their total area, so a slowdown from
  more on screen is told apart from slower code
- **Audio health:** live voices playing, mixer channels busy, and buffer underruns or late
  chunks (the live audio streamer knows when it queued a chunk late; the dropout probe's checks
  become per-frame readings)

Size: every field costs bytes in every frame of every recording (golden fixtures stay under
100 KB). Open: which fields are written always and which only under a `--record-measurements`
option, and the rounding of each (`processing_seconds` keeps microseconds).

## Docs site

The mkdocs hook that generates the complexity graphs also generates a "Performance" section
from the run ledger and the golden replays: frame time by commit per game, the frame × run
heatmap, headroom per scene, and pacing steadiness.

## Order

Part 0 first (the others report by commit and machine), then Parts 1 and 2 (the ledger and the
change map), then 4 and 5 (cheap, same data), then 7 (step timings feed Part 3's forecasts),
then 3 (measurement, then the runtime queue), then 6.
