# Describe a sprite in the console and it appears in the game

Status: APPROVED (2026-11-17, the owner). Where each part lands (the owner, 2026-11-17):

- **Part 1** (the client without a server): its own branch, `feat/sprite-client-without-server`,
  first. Merged 2026-11-17 (#216, `4f53b448`; Tasks 1-3 below). The owner's call on keeping or
  removing `glitchygames-server` is still open: nothing uses it now, and it keeps `fastapi` and
  `uvicorn` in the engine's core dependencies.
- **Part 2** (`/sprite`): the color profiles branch (the zombies session's, stacked on
  `feature/zombies-aint-my-neighbors`), "1 branch" with that work. That branch builds the shared
  sprite-text code in both directions (sprite to TOML text, TOML text to sprite: this design's
  step 6 and settled point 3) and the AI's tool calling over the live link; `/sprite` is added on
  top once the shared code lands. Whether `/sprite` also becomes a tool the AI calls is decided
  then; the recorded spawn event stays either way. Also there, once that branch's TOML
  converters land: `--extract-frames` writing `.toml` frames by default (from an APNG and from a
  `.toml` sprite), which part 1 leaves at `.png` frames so the conversion is built once.

## Intent

The owner wants to type a description in the running game's AI console ("a blue dragon") and see
that sprite appear in the game a little later: generated by the local AI, saved to the game's
sprite folder so it can be reused, and placed at the centre of what the camera shows. "For now"
the sprite only appears; what a game does with it comes later.

While finding why `uv run glitchygames-client "blue dragon"` failed (a 404), it showed that the
sprite path was never finished when aisuite was removed: the sprite service already talks to the
local AI service, but `glitchygames-client` still goes through `glitchygames-server`, a FastAPI
wrapper on port 8000, which nothing else uses and which collides with another project on the
owner's Mac (Exoneris holds 8000). The owner chose to drop that hop: the client calls the sprite
service directly (part 1). The console command uses the same service (part 2).

## Goals

1. `glitchygames-client "<description>"` generates in its own process through
   `SpriteGenerationService`, which talks to the local AI service (127.0.0.1:23231). No server,
   no port of its own.
2. In the AI console, `/sprite <description>` generates a sprite without the game waiting,
   saves it as `<game package>/sprites/<name>.toml`, and adds it to the running scene at the
   centre of the camera's view.
3. A recording of a run that used `/sprite` replays exactly: the sprite appears again at the
   same frame and place, without the AI and without the saved file.

## Non-goals

- Behaviour for the sprite: it does not move, collide or interact. Each game deciding what a
  summoned sprite becomes is later work.
- Better generation quality. The plan `plans/lucid-circuit.md` (section 9) measured three 27B
  requests at 148-292 s, all failing validation; this design shows such failures plainly and
  goes no further.
- Moving the sprite routes into the AI service (the service shares no engine code:
  `lucid-circuit.md`, row 10).

## Anti-goals (a failure even if it works)

- A frame that waits on the AI, the disk or the network.
- A recording that no longer replays after `/sprite` was used, or a replay that calls the AI.
- Keys typed in the console reaching the game (the console's rule 3 stays).
- The sprite drawn straight to the screen instead of being a sprite in the scene's groups
  (CLAUDE.md: every game object is a sprite).

## Constraints (from the project)

- The console (`src/glitchygames/ai_console.py`) is read-only (its rule 1) and sits beneath the
  recorder (rule 2). `/sprite` is a deliberate exception to rule 1, which the docstring must say;
  rule 2 stays true for everything the console does except the spawn event, which goes above
  the recorder on purpose.
- Code outside the game's logic that drives it posts with `recording.post_input_event`; a
  recording marks it `origin: external` and a replay serves the recorded event whether or not
  the poster runs again. Custom event types are registered by name with
  `events.base.named_custom_event_type`, so a recording replays them in any process.
- The console exists only with AI on (never with `--headless`, in a replay or in the browser), so
  `/sprite` never runs during a replay; the replay only serves its event.
- World-space sprites: the engine owns their `rect`; position with `world_x`/`world_y`.
- Unhandled events raise under `--no-unhandled-events` (on in every test): the spawn event needs
  an engine handler that every game gets.
- Engine changes are shared by every game: the branch's rule is to run the zombies game's own
  tests, so the engine tests for each changed engine module are run too and named in the commit.

## Approaches (the owner chose A)

- **A. A recorded spawn (chosen).** The console's worker generates and saves; the main thread
  posts one event with `post_input_event` carrying the sprite's TOML text and its world
  position; an engine handler builds the sprite and adds it to the scene. Recordings keep the
  event, so a replay re-adds the sprite from the recorded TOML. Cost: an event type, a handler,
  a text loader for sprites, an exception to the console's read-only rule.
- **B. The console adds the sprite directly (rejected).** Least code, but the recorder never sees
  it, so a recording that used `/sprite` stops replaying; `/sprite` would have to refuse while
  recording.
- **Dropped:** an event carrying only the saved file's name. Its replay breaks when the file
  moves or on another machine.

## Design

### Part 1: the client without a server

- `glitchygames.api.client` builds `SpriteGenerationService` (and `RendererService`) itself and
  calls them, in place of HTTP requests to `/sprites/generate`, `/refine` and `/extract-frames`.
  Its exit codes keep their meanings; "the AI service cannot be reached" becomes
  `SERVICE_UNAVAILABLE` with the AI service's address in the message (today a foreign server's
  404 came out as `GENERATION_REJECTED`).
- `--server-url` goes. `glitchygames-server`, its routes and `API_README.md`: the builder
  proposes keep or remove once the client no longer needs them (nothing else uses them;
  `future-work.md` names `src/glitchygames/api/` as a possible base for a remote-play API).

### Part 2: `/sprite <description>`

1. **Command.** A console command, `/sprite <description>`, listed by `/help`. One generation at
   a time, as `/ask` runs one request at a time; `/cancel` stops it (the result is discarded
   when it arrives). An empty description prints the usage.
2. **Generation, off the main thread.** The console's worker calls
   `SpriteGenerationService.generate_sprite(prompt=...)`. Progress and the outcome are lines in
   the console ("#3 generating a blue dragon...", then the file's path, or the service's error,
   including validation failures).
3. **Saving, off the main thread.** The TOML is written to `<game package>/sprites/<name>.toml`:
   the package is the running game's (`replay.tools.identity.game_package` and
   `package_directory`), the folder is created if missing, `<name>` comes from the sprite's own
   name (or the description), and an existing file is never overwritten (a numbered name, as
   the client already does). Writing goes aside then into place (`output_files`). A folder that
   cannot be written (an installed, read-only package) is said in the console; the sprite still
   appears.
4. **The spawn event.** Back on the main thread (the worker's deque), the console posts one
   event with `post_input_event`: a new engine type registered by name (for example
   `glitchygames.sprite_spawn`), carrying the TOML text, the sprite's name and the world
   position. The position is the camera's centre at posting time: `camera.world_x +
   camera.screen_width / 2`, `camera.world_y + camera.screen_height / 2` (the screen's centre
   in a game whose camera never moves).
5. **The handler.** An engine-level handler that every game gets (it never reaches the game's
   own handlers) builds the sprite from the TOML text and adds it to the active scene's sprite
   groups as a world-space sprite centred at the position. If the TOML cannot be built, the
   handler logs it and adds nothing; the game goes on.
6. **Loading from text.** The sprite factory gains a load from TOML text that shares the file
   loader's code (one path: the file loader reads the text and calls it), so the handler never
   writes a temporary file.
7. **Replay.** A recording keeps the spawn event; a replay serves it at its frame and the handler
   builds the same sprite at the same place. Nothing in a replay calls the AI or reads the
   saved file.

### Tests (behaviours)

- The client generates through the service with no server running, and reports
  `SERVICE_UNAVAILABLE` naming the AI service when it is down (the service stood in from its
  contract, `local_service`'s responses).
- `/sprite` with a stand-in service: the file is written under the game's package, a second
  sprite of the same name gets a new file, the event is posted with the TOML and the camera's
  centre, and the frame never waited (the worker did the work).
- The handler adds a world-space sprite centred at the position, on a moved camera and a still
  one; bad TOML adds nothing and is logged.
- A recording made with a spawn replays with the sprite at the same frame and place, with no AI
  and the saved file deleted.
- `/sprite` refuses an empty description, refuses while one runs, and `/cancel` discards the
  late result; a read-only sprite folder is reported and the sprite still appears.
- The text loader and the file loader give the same sprite.

## Settled after the builder check (the designer's calls, for the owner to check)

1. **Which scene and camera.** The game's own scene, the one `/inspect` describes
   (`debug_subject`: under the pause screen, the paused game's scene, not the pause overlay),
   and that scene's camera. With no scene yet, `/sprite` refuses before generating ("No scene
   yet"), as `/inspect` does. The handler adds the sprite to the same scene (the scene manager's
   game scene, not a pause overlay), live and replayed alike.
2. **How long it lives.** As long as the scene it was added to: a scene change, reload or
   restart drops it; the saved file stays. "For now" (the owner) asks for it to appear, not to
   persist, so no engine-level registry and no new `ContextSlot`.
3. **Sprite class, size and animation.** A plain `AnimatedSprite` (what
   `SpriteFactory.load_sprite` returns) with `COORDINATE_SPACE = WORLD`, at its native pixel
   size, animating as any loaded sprite does, centred on the position by its rect's size. The
   text loader means `AnimatedSprite`'s file-based loading (`_analyze_toml_file`,
   `_get_toml_data`, the constructor) takes text in one shared path; that refactor touches every
   game and Bitmappy, so their sprite tests run too.
4. **The full TOML in the event.** Yes, uncapped: a few kilobytes, compressed in the
   `.jsonl.gz`, only in recordings that used `/sprite`. Replay tools treat it as any external
   event; no side file (a side file would break a replay elsewhere, as the dropped approach).
5. **Who posts.** The console calls `recording.post_input_event` from its main-thread update (the
   worker never posts). The posted event goes up through the host and recording doors as any
   posted event does, so the recorder keeps it. `tests/test_engine_doors.py` has no list of
   callers for it (checked).
6. **Timing and position.** The camera's centre when the console posts (a following camera may
   have moved a frame by then: accepted). The sprite gets a stable id and is in replay
   comparison as any sprite; a replay serves the event at its frame, so it matches. No extra
   pixel snapping beyond the scene's own `PIXEL_SNAP_MODE`.
7. **Failure paths.** A generation that reports failure spawns nothing, even with TOML in its
   result. A folder that cannot be written: the console prints why and that the sprite was not
   saved; the event still carries the sprite's name from its TOML.
8. **Which games.** Every game that has the console (the host layer gives it to all of them), so
   the handler is engine-level and every game's tests that cover event dispatch run. The file
   goes under the running game's package (`<package>/sprites/`), Bitmappy included. In the
   Arcade the console belongs to the outer live game; inner games are replays and have none.
9. **Part 1's contract.** Only `API_README.md` names `glitchygames-client` or `--server-url`
   outside the API's own code and tests (checked), so `--server-url` goes and the README is
   updated; the exit codes keep their meanings.

## Part 1 implementation plan (branch `feat/sprite-client-without-server`)

> task; steps are checkboxes. Decisions, files, interfaces and tests are named here; bodies are

**Goal:** `glitchygames-client` generates and extracts in its own process, with no
`glitchygames-server` to start and no port of its own; it writes `.toml` sprites by default, and
`--extract-frames` reads a `.toml` sprite as well as an APNG (the owner, 2026-11-17).

**Architecture:** the work the sprite routes do today (generation and building the response:
TOML, rendered PNG, files saved on request; refinement; APNG frame extraction) moves out of
`api/routes/sprites.py` into one module, `api/sprite_requests.py`, that both the routes and the
client call: one code path, so the server and the client never drift. The routes keep only
mapping errors to HTTP statuses; the client maps the same errors to exit codes.

**Tech stack:** Python 3.14/3.15, pydantic models in `api/models`, `SpriteGenerationService`
(talks to the AI service through `glitchygames.ai.local_service`), pytest with `mocker`.

### Global constraints

- Exit codes keep their meanings (`ExitCode`, never the number): `GENERATION_REJECTED`,
  `EXTRACTION_REJECTED`, `SERVICE_UNAVAILABLE`, `MISSING_INPUT`, `UNUSABLE_INPUT`,
  `CANNOT_WRITE_OUTPUT`, `INTERNAL_ERROR`, `ARGUMENT_PARSER_ERROR`. `OPTIONS_REFUSED` (a bad
  `--server-url`) goes with the option.
- `SERVICE_UNAVAILABLE` covers every `AIProviderError` (as the route's 503 did) and names the AI
  service's address, `local_service.DEFAULT_BASE_URL` (`http://127.0.0.1:23231`).
- The server's behaviour is unchanged: every existing test in `tests/api/test_api_routes_sprites.py`,
  `tests/api/test_sprite_routes.py` and `tests/api/test_api_main.py` passes untouched.
- Tests stand the AI service in as the sprite service's own tests do: patch
  `glitchygames.ai.local_service.create_chat_client` (its contract: a chat client whose
  completion returns the model's text, or raising `LocalAIServiceError`).
- Output formats (the owner, 2026-11-17: "Both supported, toml default"): generation writes
  `.toml` by default (`DEFAULT_OUTPUT_FORMATS = ['toml']`); `-f png` (or `-f toml -f png`) adds
  the image. `--extract-frames` takes an APNG or a `.toml` sprite (told apart by the file's
  `.toml` suffix) and writes `.png` frames, as today; `.toml` frames wait for the color profiles
  branch's converters (status, above).
- uv only; ruff, basedpyright, ty, then tests; 100% coverage; no asserts outside tests.

### Review focus

1. The AI service not installed (`LocalAIServiceNotInstalledError`): `SERVICE_UNAVAILABLE` with a
   message saying so, not a traceback. Test in Task 2.
2. An unknown `--animation-language-model` (the service answers an error status):
   `SERVICE_UNAVAILABLE` with the service's own message, as the route's 503 gave. Test in Task 2.

   frames): `EXTRACTION_REJECTED`, with no server. Tests in Task 1 (the responses) and Task 2
   (the exit code).
