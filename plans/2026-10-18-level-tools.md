# Level Tools — Master Plan

- **Date:** 2026-10-18
- **Status:** Design brief (to be brainstormed into specs, one sub-plan at a time)
- **Roadmap:** `plans/engine-audit.md` item #11 (level/room data format and tilemaps); helps #1
  (solid collision)
- **Inspiration:** the Galimore tools (1999–2000), surveyed in `docs/galimore.md`:
  **Mapedit** (map editor), **Galimake** (tile packer) and **GATTRIB**
  (tile attribute editor). Galibmap (pixel editor) is already covered by Bitmappy.

## Goal

Give GlitchyGames a shared, data-driven way to build levels: a tilemap file format the engine loads
and renders, a map editor to paint it, and tileset tooling that keeps tile IDs stable. Today each
game hand-codes its levels (`ScreenData` in Brave Adventurer, `FloorData` in Clockwork Keep, a
`LevelManager` in Papyrus); collision terrain is hand-placed rectangles in code.

## What Galimore got right (keep)

1. **Layered maps:** background → foreground → objects → actors, drawn in order.
2. **Floors:** two stacked floors per map with a per-cell "layer switch" flag (walk under or over
   bridges).
3. **Per-cell properties separate from the art:** unpassable (by faction), deep, bridge, chasm,
   pushable, transparent, door, burnable. Collision lives on the map cell, so art can be reused
   and invisible walls are possible.
4. **Named exits with entry points:** `Exit{name, x, y}` in the 1999 format; rooms link to rooms.
5. **Stable tile IDs:** Galimake blanked removed tiles instead of deleting them, so existing maps
   never had their indices shift.
6. **Editor ergonomics:** brush sizes 1–4, layer and floor visibility toggles, a tileset palette,
   eraser = tile 0, and a property-paint mode with pick-up (right-click) and stamp (drag).

## What to do differently

- **Text formats, not memory dumps.** Galimore's files were raw C++ struct dumps identified only by
  their size (fragile, compiler- and endian-specific). Use TOML like the sprite format.
- **Explicit IDs, never list position.** A tile's ID is written next to it in the tileset, so
  reordering or removing tiles can never remap a level.
- **Tiles are GlitchyGames sprites.** A tileset references sprite TOML files (static or animated),
  so animated tiles (torches, water) come for free.
- **Properties are named, not bit numbers.** `unpassable = true` in TOML; the engine turns them
  into collision solids for `CollisionManager` and the coming solid-collision work (#1).

## Design for today's constraints, not 1999's

Galimore's formats were shaped by the limits of a 1999 DOS PC; GlitchyGames' sprite format already
dropped those limits, and the level formats should get the same overhaul rather than a port. Borrow
the *ideas*, re-derive the *encodings*:

| 1999 constraint | What it forced in Galimore | Today |
|---|---|---|
| Kilobytes of RAM, XMS paging | `UINT8` tile indices (max 255 tiles per layer), fixed 64×64 maps, two floors, packed bit masks | Memory is not the constraint: open-ended tile IDs, map sizes and layer counts; named properties instead of bits |
| Slow disks, no parser budget | Raw `fwrite` struct dumps, file type detected by size | Human-readable TOML, versioned (`format_version`), diff-friendly in git, reviewable in pull requests |
| 640×480 screens, 256 colours | 32×32 tiles, palette indices, one transparent palette slot | Any tile size, RGBA with per-pixel alpha, magenta key kept only as a convention |
| One developer, one machine | Formats tied to one compiler and CPU (padding, endianness) | Portable formats; generated by tools, by hand, or by AI (Bitmappy already generates sprites) |
| Keyboard and mouse | Editor keys only | Controllers (Bitmappy's multi-controller editing), touch later |
| No version control | Daily zip snapshots (the archives) | Git: stable IDs and text formats so changes diff cleanly |

## Audit of the borrowed ideas (2026-10-18)

Galimore was a top-down, grid-based RPG. Three of GlitchyGames' four games are side-scrolling
platformers whose levels are **pixel-positioned objects, not tiles**: Brave Adventurer's
`ScreenData` holds ground segments `(local_x, width)`, walls `(local_x, height)`, enemies and
collectibles at pixel positions (`examples/brave_adventurer/levels.py`); Clockwork Keep's
`FloorData` holds platforms `(x, y, width)`, elevators, collectibles, enemies and a spawn point
(`examples/clockwork_keep/levels.py`). None of them would use a tile grid as Galimore drew it. Each
borrowed idea, checked against that:

| Borrowed idea | Problem for GlitchyGames | Adjustment |
|---|---|---|
| Map = tile grid layers | Every current game places terrain and actors by pixel, with arbitrary widths; a grid-only format would not express a single existing level | **Object layers are first-class, not an add-on.** A map is an ordered list of layers, each either a *tile layer* (grid) or an *object layer* (named, typed, pixel-positioned rectangles and points with properties: ground segments, walls, platforms, elevators, spawns, enemies, pickups, triggers). The first migrations are object-only. |
| Exactly two floors + a per-cell layer-switch bit | Fixed count, RPG-specific; platformers have no floors | **Layers in a z-order relative to the actor layer**, any number. "Walk behind/over" becomes a property of a layer or region, not a fixed two-floor model. |
| Per-cell property mask (unpassable by faction, deep, chasm…) | RPG vocabulary; platformers need solid, one-way platform, ladder, hazard, moving platform, kill zone | **Open, typed property vocabulary with a project schema**, not a fixed bit set. Ship a small common core (`solid`, `one_way`, `hazard`, `climbable`, `water`) plus game-defined extras. Properties can sit on tiles (defaults), tile cells (overrides) and objects. Precedence: object > cell override > tile default. |
| Collision from property cells merged into rectangles | Must agree with this branch's hitbox model and the coming solid-collision design (#1) | Tile collision shape is the **full cell** unless the tile sprite defines an explicit hitbox; **never the visible-pixel fallback** (a grass tile with a transparent top row must still be solid at the cell top). Object-layer rects are used as authored. Merged rects feed `CollisionManager` layers named by property. |
| Exits = a cell + an entry cell | Side-scrollers change screens at edges (Brave Adventurer), floors via elevators (Clockwork Keep); a single cell is too narrow | **Exits are regions** (an object-layer rect or a map edge) naming a target map and a **named spawn point** there, plus an optional transition (the engine already has fade/slide/wipe/elevator). |
| One character per cell + a legend | Fine for small maps; runs out of readable characters with large tilesets, and a 20-screen level is ~500 cells wide | Character grids stay the default (diff-friendly, like sprites), with **per-layer legends** and **chunked rows** for wide maps; allow an explicit `encoding = "csv"` for layers with more distinct tiles than readable characters. |
| Stable IDs by blanking removed tiles | Good. In Galimore the identity was pixel equality (identical tiles collapsed) | Keep explicit IDs and `retired` tombstones; identity by sprite file (see sub-plan C). Map cells reference `(tileset key, id)`; renaming a tileset key is a lint error, not a silent break. |
| Packer step (Galimake rebuilds `.dat` from a folder) | With TOML, the tileset file is human-editable; a mandatory rebuild creates two sources of truth | **The tileset file is the source of truth.** Tilesmith edits and lints it; it never regenerates it from scratch. |
| Mapedit's mask overlay colours (magenta / purple / black) | Magenta is GlitchyGames' transparency key | Draw property overlays with the debug overlay's palette and legend. |
| Square brushes 1–4 | Fine, but the one big modern feature Galimore lacked is **auto-tiling** (terrain brushes that pick edge and corner tiles) | Keep brushes; add rectangle, line and fill; plan auto-tiling (bitmask / Wang tiles) for later in Mapsmith. |
| Build our own editor | [Tiled](https://www.mapeditor.org/) is a mature, free map editor with a documented JSON format | Still build Mapsmith (it shares Bitmappy's UI, controllers and sprite format), but add **Tiled JSON import** in sub-plan A so existing Tiled maps can be used and compared against. |

## Sub-plans (build in this order)

| # | Sub-plan | Galimore ancestor | Delivers |
|---|---|---|---|
| A | [Tilemap format and runtime](2026-10-18-level-tools-a-tilemap-format.md) | Mapedit's `GALIMORE_MAP`, 1999 GMAP exits | TOML tileset + map formats, loader, `TilemapLayer` rendering through `Camera2D`, properties → collision, exits |
| B | [Map editor](2026-10-18-level-tools-b-map-editor.md) | Mapedit, GMAP | Mapsmith: an editor for painting layers, floors, properties and exits |
| C | [Tileset builder](2026-10-18-level-tools-c-tileset-builder.md) | Galimake, MAKEDAT, GATTRIB | Tilesmith: builds and lints tilesets from sprite files with stable IDs and per-tile game data |
| D | [Bitmappy updates](2026-10-18-level-tools-d-bitmappy-updates.md) | Galibmap, GEDIT | Galibmap/GEDIT features Bitmappy lacks, adjusted for this engine (hitbox editing, mirror/rotate, replace colour, directional templates, tile mode…) |
| E | [Translating Galimore forward](2026-10-18-level-tools-e-galimore-import.md) | All 1999 and 2000 data | Converters that bring Galimore's tiles, sprites, maps and exits into the new formats, as real examples and test fixtures |

A comes first: B and C both read and write its formats, and games can adopt A (hand-written TOML)
before any editor exists. B and C are independent of each other after A. D is independent of A–C
and can start any time; its tile-mode item is easier after A. E's sprite and tile converters can
start any time (they target the existing sprite format); its map converter follows A.

Chosen by the user on 2026-10-18:

| Tool | Name |
|---|---|
| Map editor (B) | **Mapsmith** |
| Tileset builder (C) | **Tilesmith** |
| Tilemap runtime (A) | Engine module with plain names: `glitchygames/tilemaps/` (`Tilemap`, `Tileset`, `TilemapLayer`) |
| The suite | **Glitchy Studio**: Bitmappy + Mapsmith + Tilesmith (umbrella name for docs and a launcher) |

Bitmappy keeps its name. Names were checked against this repo only, not against trademarks.

## Open questions (for brainstorming)

- Fixed tile size per tileset (Galimore: 32×32) or per layer? Mixed sizes (32×48 characters on a
  32×32 grid) belong to the actor layer, not the tile layers.
- Map size limits and sparse storage: a 64×64×2-floor map as character grids is fine; large worlds
  may want chunks.
- How a game opts in: replace `ScreenData`/`FloorData` gradually, starting with one Brave Adventurer
  screen or one Clockwork Keep floor — as an object-layer-only map (see the audit above).
- Where the engine-world-space work (#6) lands first; tilemap rendering should use it rather than
  each game's own camera loop.
