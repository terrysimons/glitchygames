    Bitmappy Architecture#

    Bitmappy is GlitchyGames' pixel art editor. These diagrams show how it is wired up through the engine, from bootstrap to rendering.

    Its package#

    Bitmappy is an app, not part of the engine: the first member of the apps layer of the uv workspace, at src/apps/bitmappy/. The distribution, the import package and the console script are all bitmappy (uv run bitmappy), and its scene's logical name, the one a recording holds, is apps.bitmappy.editor:BitmapEditorScene. A recording made when the scene lived in the engine (glitchygames.bitmappy.editor:BitmapEditorScene) is refused by a plain replay, which names the remedy; --replay-trace OLD --rebaseline NEW --headless converts it (gameplay replay).

    • Its code is src/apps/bitmappy/src/bitmappy/. The engine never imports it, and Bitmappy uses the engine's public API (sprite file-format detection, for one, is the engine's src/glitchygames/sprites/file_format.py).
    • Its sprite library is 71 sprites in src/apps/bitmappy/src/bitmappy/resources/sprites/, shipped as package data and found through bitmappy.SPRITE_CONFIG_DIR. They are also the AI's training data (load_ai_training_data() below), so they stay in the package.
    • Its other resources (the window icon and bitmappy.cfg) are beside them, in src/apps/bitmappy/src/bitmappy/resources/.
    • Its tests are in src/apps/bitmappy/tests/, rootless, every file named test_bitmappy_*.py.
    • The Load and Save dialogs (the engine's glitchygames.ui dialog scenes) treat every file the same: the name is used as given, with surrounding whitespace trimmed, and a sprite in the library is opened by its path. The example: prefix they once understood is gone, and Save applies a per-platform rule to : in a file name (_file_name_problem, the platform passed in and sys.platform by default); nothing is written, the full refusal is shown in the editor's debug text, and the dialog stays open with the name kept and a short reason in its prompt (REFUSED_FILE_NAME_PROMPT), so the name can be corrected in place:
    Platform : in a Save name
    Windows (win32, cygwin) Allowed only in a letter-drive designator (C:\a.toml, C:/a.toml, C:a.toml, \\?\C:\a.toml, \\.\C:\a.toml); anywhere else, including inside a UNC server or share name, it is refused: NTFS would read it as an alternate data stream, so examples:foo.toml would leave an empty file called examples
    macOS (darwin) Refused everywhere: Finder shows : as / (a Classic Mac OS leftover)
    Linux and others Allowed
    Browser (emscripten) Allowed (Save is a download; the browser sanitizes the name)

    Load is unchanged (a missing name is reported as "File not found").

    Bootstrap & Main Loop#

    How Bitmappy starts up: entry point through main(), GameEngine initialization, scene setup, and the main loop (one frame per pass, ended by _finish_frame). The Bitmappy box is the editor's own code (src/apps/bitmappy/src/bitmappy/); the Engine box is what every game gets.

    participant User
    box rgb(255,243,224) Bitmappy
    participant main as main()
    participant BES as BitmapEditorScene
    end
    box rgb(232,238,255) Engine
    participant GE as GameEngine
    participant SM as SceneManager (singleton)
    end

    User->>main: uv run bitmappy
    main->>GE: GameEngine(game=BitmapEditorScene, icon=...)
    GE->>GE: parse CLI args (GameEngine.args() + BitmapEditorScene.args())
    GE->>GE: pygame.init(), create display
    main->>main: load_ai_training_data()
    main->>GE: engine.start()
    GE->>BES: BitmapEditorScene(options=OPTIONS)
    BES->>BES: EditorSetup.init_undo_redo_system()
    BES->>BES: EditorSetup.setup_menu_bar()
    BES->>BES: EditorSetup.setup_canvas(options)
    BES->>BES: SliderManager.setup_sliders_and_color_well()
    BES->>BES: EditorSetup.setup_debug_text_box()
    BES->>BES: FilmStripCoordinator.setup_film_strips()
    GE->>GE: _initialize_event_managers()
    GE->>SM: scene_manager.switch_to_scene(game)
    SM->>BES: setup() (AIManager.setup() starts the AI worker)
    GE->>SM: scene_manager.start()

    loop Main Game Loop (while active_scene is not None)
        Note over SM: dt = the previous frame's start-to-start time
        SM->>SM: camera.begin_frame()
        SM->>BES: _update_scene() (Scene.dt_tick: logic and collision)
        SM->>GE: _process_events()
        GE->>GE: _pump_events() (active_sources().pump_events(): live, pygame.event.get())
        GE->>SM: event_handlers[event.type](event)
        SM->>BES: on_*_event(event)
        SM->>SM: _run_supervisor_slot() (supervisors, e.g. a recording's)
        SM->>SM: _update_frame_services() (shake, rumble)
        SM->>SM: _aim_active_camera() (camera_target / follow)
        SM->>SM: _position_active_world_sprites() (world sprites' rect, culling)
        SM->>SM: _render_scene() (BitmapEditorScene.update: animation, controllers, AI, then draw)
        SM->>SM: _advance_still_camera_shake() (WORLD shake nothing advanced)
        SM->>SM: _present_frame() (overlay, display update)
        SM->>SM: _finish_frame() (pace, then set dt once from perf_counter)
    end

    Class Hierarchy#

    Event dispatch chain (how events reach your scene)#

    Every scene has every on_*_event() handler, but it gets them a different way from the engine. A Scene inherits them: AllEventStubs gives it a default for each one, which reports the event as unhandled, and your scene overrides the ones it uses. GameEngine and SceneManager inherit no handlers at all. They pass on_*_event() calls along at runtime through __getattr__.

    • Solid arrows are inheritance, pointing at the base class.
    • Dotted arrows are the runtime calls, numbered in the order an event takes them.
    • The Engine box is the engine's classes; the Bitmappy box is the editor's scene.
    classDiagram

    EventStubs ..> GameOptionsProvider : unhandled#95;event(game)

    The interfaces are abstract base classes, not typing.Protocols, but EventInterface's __subclasshook__ makes them structural: any class with every handler of an interface counts as one. GameOptionsProvider is a real Protocol: unhandled_event() needs only the scene's options. Both scene classes also inherit SceneInterface (left out to keep the diagram readable).

    Event flow — how an SDL event reaches your handler in Bitmappy (the stub a missing handler falls to is the engine's):

    flowchart TD
    SDL["SDL Event"] --> GE
    subgraph ENGINE_BITMAPPY_EVENT_FLOW["Engine"]
        GE["GameEngine\nO#40;1#41; event_handlers lookup"]
        GE --> MGR["Event Manager\ne.g. MouseEventManager"]
        MGR -->|"updates state,\nsynthesizes events"| SM["SceneManager\nforwards to active_scene"]
        STUB["No handler?\nThe stub calls unhandled_event#40;#41;"]
    end
    subgraph APP_BITMAPPY_EVENT_FLOW["Bitmappy"]
        BES["BitmapEditorScene\n#40;the active scene#41;"]
        BES --> HANDLER["Your handler runs\non_left_mouse_drag_event#40;#41;"]
    end
    SM --> BES
    BES --> STUB

    The GameEngine receives every SDL event and does an O(1) dict lookup to find the right event manager. The event manager updates its internal state (button tracking, axis values, drag detection) and may synthesize higher-level events (drag, drop, chord). It then forwards to the SceneManager, which passes everything to the active_scene. In Bitmappy, that's BitmapEditorScene, which overrides handlers like on_key_down_event(), on_left_mouse_button_down_event(), on_left_mouse_drag_event(), and on_controller_button_down_event(). Events it doesn't override hit the stubs, which call unhandled_event(): it does nothing by default, logs each event type once when debug_events is on (the --debug-events flag, off by default), and raises UnhandledEventError under --no-unhandled-events (as the tests run).

    Sprite hierarchy (renderable objects)#

    DirtySprite is pygame's base for all sprites that support dirty-rect rendering. GlitchyGames extends it through RootSprite → Sprite → BitmappySprite to add mouse events, non-optional image/rect, named parent tracking and TOML load/save. AnimatedSprite derives from DirtySprite directly. DirtySprite is pygame's, outside both boxes; the Bitmappy box holds the editor's own sprites.

The top Engine box is the dispatch every game gets, the Bitmappy box is the editor's handlers, and the bottom Engine box is the engine's UI widgets (glitchygames.ui) the editor's clicks reach.

    Rendering Pipeline#

    The steps of each frame, in order (SceneManager._run_scene_frame, then _finish_frame). Bitmappy has no world-space sprites, so steps 5 and 6 leave its widgets alone. Dirty-rect optimization ensures only changed regions are redrawn and pushed to the display. The engine runs every step; the Bitmappy box is the editor's update(), which step 7 calls.

    flowchart TD
    subgraph ENGINE_BITMAPPY_FRAME["Engine"]
        BEGIN["1. camera.begin_frame()\nclear the camera's update and shake-advance flags"] --> LOGIC
        LOGIC["2. _update_scene()\nScene.dt_tick(dt): logic, animation, collision\n(dt capped by MAX_FRAME_SECONDS when set)"] --> EVENTS
        EVENTS["3. _process_events(), then _run_supervisor_slot()\nthe engine's event_handlers dict - O(1) lookup\nBitmapEditorScene handlers modify sprites"] --> SERVICES
        SERVICES["4. _update_frame_services()\nshake and rumble"] --> AIM
        AIM["5. _aim_active_camera()\ncamera_target() / follow target\n(skipped when the scene was switched mid-frame)"] --> POSITION
        POSITION["6. _position_active_world_sprites()\nworld sprites' rect from the camera, culling\n(screen-space sprites untouched)"] --> RENDER
        RENDER["7. _render_scene()\nScene.update() (visual only), LayeredDirty.draw"] --> CHECK{"sprite.dirty?"}
        CHECK -->|"dirty=0"| SKIP["Skip - no redraw"]
        CHECK -->|"dirty=1 or 2"| REDRAW["Blit sprite.image at sprite.rect\ncollect changed rects"]
        SKIP --> STILL
        REDRAW --> STILL
        STILL["8. _advance_still_camera_shake()\nadvance a WORLD shake nothing advanced this frame\n(no aim, no game camera.update())"] --> PRESENT
        PRESENT["9. _present_frame()\ndebug overlay, pygame.display.update rects or flip"] --> FINISH
        FINISH["10. _finish_frame()\npace, then one perf_counter reading sets the next dt"]
    end
    subgraph APP_BITMAPPY_FRAME["Bitmappy"]
        FM["BitmapEditorScene.update()\ncanvas.update_animation(dt)\nFilmStripCoordinator.update_film_strip_animation_timing()\nFilmStripSprite.dirty = 1 when a frame advances"]
    end
    RENDER --> FM

    Multi-Controller System#

    Up to 4 color-coded controllers can operate simultaneously. Each controller independently switches between film strip, canvas and slider (A, R, G, B) modes using the triggers: L2 steps forward, R2 steps back (R2 does nothing in film strip mode). B undoes and X redoes in film strip and canvas modes.
