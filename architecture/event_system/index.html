Event System Architecture#

GlitchyGames makes it easy to port simple pygame projects into more advanced games with little effort. If you already have a pygame game using pygame.event.get() and if/elif chains, you can bring it into GlitchyGames and immediately benefit from named event handlers, automatic state tracking, and synthesized higher-level events — without rewriting your existing event logic.

Porting can be incremental: a scene that defines process_event(event) receives every raw pygame.event.Event from the engine, in order, instead of the on_*_event() callbacks (GameEngine.process_events), so an existing if/elif loop body moves in as it is. Adopt the GlitchyGames handlers one event at a time as you need their benefits. Don't call pygame.event.get() yourself: the engine reads SDL's queue once per frame, and whatever another reader takes never reaches the engine.

Replay

Code that polls pygame directly cannot be replayed exactly. For sessions that replay (--replay-trace), read polled input from current_input() and take events through the engine; see Gameplay Recording and Replay. Code inside the glitchygames package must always do so (tests/test_engine_doors.py).

What GlitchyGames adds on top of raw pygame:

  • Named handlers — override on_key_down_event() instead of writing if event.type == pygame.KEYDOWN. No if/elif dispatch chains.
  • Automatic state tracking — event managers cache button states, axis values, hat positions, and mouse focus so you can poll the current state very cheaply at any time.
  • Synthesized events — GlitchyGames generates events that pygame doesn't provide: mouse drag and drop (on_mouse_drag_event, on_left_mouse_drag_event, on_mouse_drop_event), keyboard chords (on_key_chord_down_event), and per-button mouse events (on_left_mouse_button_down_event vs raw MOUSEBUTTONDOWN with a button field).
  • Custom event types — three engine-level event types (FPSEVENT, GAMEEVENT, MENUEVENT) allocated with pygame.event.custom_type(), plus an extensible GAMEEVENT bus for posting arbitrary game-specific events with per-subtype callbacks.
  • An unhandled event safety net — every on_*_event() has a default stub that reports the event as unhandled (a warning once per type, or an UnhandledEventError under --no-unhandled-events), and the engine counts every unhandled event type and logs the table at teardown.

Events flow from SDL through pygame, into specialized event managers that track state and synthesize higher-level events, through the scene manager, and finally into scenes and sprites.

The proxy layers#

Every manager is a ResourceManager that passes calls on to a proxy. The proxy implements the family's interface (MouseEvents for the mouse), keeps the family's state, synthesizes higher-level events (drag, drop and focus for the mouse; chords for the keyboard) and calls the same handler on its game, which is the SceneManager. The SceneManager hands every on_*_event() to the active scene (__getattr__). The mouse, as an example:

Joysticks and controllers#

Custom Event Types#

GlitchyGames defines three custom event types beyond the standard pygame events, allocated with pygame.event.custom_type() when glitchygames.events is imported, so a game's or library's own custom_type() never gets one of their ids (BUGS.md #197). custom_type() hands out USEREVENT + 1, + 2, + 3, ... in order, and the engine's module is imported before any game code runs, so they are USEREVENT + 1, + 2 and + 3, the numbers recordings hold. Something that calls custom_type() before glitchygames is imported shifts them (a recording made that way replays only in a process that imports the same way).

These constants are defined in src/glitchygames/events/base.py (exported by glitchygames.events):

FPSEVENT = pygame.event.custom_type()  # FPS counter updates (USEREVENT + 1)
GAMEEVENT = pygame.event.custom_type()  # Game-specific events, extensible via subtypes (+ 2)
MENUEVENT = pygame.event.custom_type()  # Menu item selections (+ 3)

GAMEEVENT is intentionally generic — game code posts events with arbitrary payloads via GameEngine.post_game_event(), and can register per-subtype callbacks via GameEngine.register_game_event() (a scene reaches both through self.scene_manager: register_game_event() and game_engine). This gives games an extensible event bus without consuming additional pygame event IDs.

Extending GAMEEVENT in your game#

GAMEEVENT is designed as an extensible event bus. Instead of consuming additional pygame event IDs for each game-specific event, you define integer subtypes and register callbacks for them. All subtypes share the single GAMEEVENT ID.

Here's how a game might define custom events for a scoring system and a power-up system:

# Define your game's event subtypes as constants
SCORE_CHANGED = 1
POWER_UP_COLLECTED = 2
LEVEL_COMPLETE = 3

class MyGame(Scene):
    def setup(self):
        # Register callbacks for each subtype
        self.scene_manager.register_game_event(SCORE_CHANGED, self.on_score_changed)
        self.scene_manager.register_game_event(POWER_UP_COLLECTED, self.on_power_up)
        self.scene_manager.register_game_event(LEVEL_COMPLETE, self.on_level_complete)

    def on_score_changed(self, event: HashableEvent):
        new_score = event.score
        self.hud.update_score(new_score)

    def on_power_up(self, event: HashableEvent):
        power_type = event.power_type
        duration = event.duration
        self.player.apply_power_up(power_type, duration)

    def on_level_complete(self, event: HashableEvent):
        # The SceneManager switches to it after this frame
        self.next_scene = LevelTransitionScene(event.next_level)

Any code in the game can fire these events:

# From a collision handler, enemy class, pickup sprite, etc.
# (SceneManager is a singleton: SceneManager().game_engine works anywhere)
self.scene_manager.game_engine.post_game_event(
    event_subtype=SCORE_CHANGED,
    event_data={'score': self.score},
)

self.scene_manager.game_engine.post_game_event(
    event_subtype=POWER_UP_COLLECTED,
    event_data={'power_type': 'speed_boost', 'duration': 5.0},
)

Under the hood, post_game_event creates a pygame.event.Event with type GAMEEVENT and a subtype field, then posts it with glitchygames.recording.post_event (so recordings mark it internal). SceneManager.on_game_event() looks up game_engine.registered_events[event.subtype] and calls the matching callback. If no callback is registered for that subtype, it logs an error telling you to call register_game_event().

This pattern gives you an unlimited number of game-specific event types while consuming only one pygame event ID.

Native window messages (SYSWMEVENT)#

SYSWMEVENT carries the window system's raw messages: on x11 every X event the window gets (focus, exposure, property and configure notifications), on Windows each window message (hwnd, msg, wparam, lparam). SDL leaves the type disabled, and so does the engine: GameEngine allows every event type through allow_every_event_type() (src/glitchygames/events/base.py), which keeps SYSWMEVENT blocked. Before, a plain pygame.event.set_allowed(None) turned it on, so on a real X server the queue, every --record-trace recording and every instant-replay journal filled with messages no game read.

A game that wants them opts in on its scene class (the one given to GameEngine), like TARGET_FPS:

class MyGame(Scene):
    NATIVE_WINDOW_MESSAGES = True  # anything but a bool is refused with TypeError

    def on_sys_wm_event(self, event: HashableEvent) -> None:
        # A plain HashableEvent (SYSWMEVENT has no class in EVENT_CLASSES) holding
        # pygame's platform fields: event.event (the raw XEvent bytes) on x11
        ...

The route is GameEngine.process_game_event → GameEventManager.on_sys_wm_event → SceneManager → the active scene's on_sys_wm_event. A game that opts in records them like any other event (an x11 message's bytes are stored as {"__bytes__": "<hex>"}), and a replay serves the recorded ones; a replay's input blocking (src/glitchygames/replay/input_blocking.py) restores the type to blocked when it ends. pygame-ce 2.5.8 reports SYSWMEVENT as allowed until something blocks it through pygame, although SDL ignores it, which is why the engine blocks it explicitly: a snapshot-and-restore of the blocked types would otherwise turn it on.

ResourceManager Proxy Pattern#

Each event manager is a shared-instance ResourceManager that delegates to inner proxy objects. The proxy chain provides two capabilities:

  1. Event dispatch: When GameEngine calls on_*_event() on an event manager (e.g., MouseEventManager), the event manager forwards to its inner proxy, which updates internal state (tracking pressed keys, button states, drag sequences, etc.) and then forwards the event to self.game — the active scene.

  2. Attribute fallthrough: An attribute the manager doesn't have is looked up on its proxies by ResourceManager.__getattr__ (src/glitchygames/events/base.py), each in turn until one has it: mouse_manager.get_pos() falls through the inner proxy and the scene to pygame.mouse (BUGS.md #198: the lookup used to stop at the first proxy).

Poll input from the snapshot

The pygame modules in the proxy lists below read the device live. Polled input should come from glitchygames.input.state.current_input(): it is the frame's snapshot, which a replay serves exactly.

Why this matters: Scenes and sprites never need a direct reference to the event plumbing. They talk to the event manager, a shared instance accessible from anywhere (MouseEventManager() is the engine's), and the manager handles state tracking (what buttons are held, what sprite has mouse focus, what keys form a chord).

Architecture#

Each manager follows the same two-layer structure:

MouseEventManager (shared-instance ResourceManager)
├── proxies: [MouseEventProxy]
│
└── MouseEventProxy (inner class, also a ResourceManager; SHARES_INSTANCE = False)
    ├── proxies: [self.game, pygame.mouse]
    ├── state: mouse_state, dragging, focus tracking
    └── on_*_event(): update state, synthesize events, forward to self.game

The inner proxy holds the real state and logic. The outer manager is just a shared-instance wrapper that ensures only one proxy chain exists per subsystem.

Shared instances#

ResourceManager.__new__ maintains a class-level __instances__ dict keyed by concrete class type. Constructing MouseEventManager(game) a second time returns the original instance as it is: ResourceManager.__init_subclass__ wraps each class's __init__ so a shared instance is initialized once (BUGS.md #198: Python runs __init__ on whatever __new__ returns, so a second construction rebuilt the manager for game=None).

A class with SHARES_INSTANCE = False gets a new instance at every construction: the proxies (a manager owns its own; the controller manager one per controller) and EventManager (GameEngine, made for each run, and SceneManager, whose own __new__ keeps its singleton). Each engine run calls ResourceManager.release_shared_instances() before it makes its managers, so a second engine in one process (a recording, then its replay) builds its own, opening devices through its own doors.

HashableEvent Wrapper#

Raw pygame events are converted to HashableEvent (HashableEvent.from_pygame) to enable hashing, immutability and serialization. This is the universal event type throughout the system: every event of a type with a class of its own is an instance of that class (below).

pygame.event.Event is not hashable

Raw pygame.event.Event objects cannot be hashed or used as dictionary keys. HashableEvent is a UserDict subclass holding the event's type and a copy of its fields (the pygame event itself is not kept), and it provides __hash__().

The problem with raw pygame event handling#

In raw pygame, handling events looks like this:

for event in pygame.event.get():
    if event.type == pygame.KEYDOWN:
        # handle key press
        ...
    elif event.type == pygame.MOUSEMOTION:
        # handle mouse move
        ...
    elif event.type == pygame.JOYAXISMOTION:
        # handle joystick
        ...
    # ... and so on for every event type

This has several problems:

  1. Silent event dropping: Any event type you don't have an elif for is silently ignored. You get no feedback that your game is missing a handler — bugs hide behind silence.

  2. No separation of concerns: The entire event dispatch is one giant if/elif chain in one place. Every subsystem's event handling is tangled together.

  3. No state tracking: Raw pygame events are fire-and-forget. If you want to know "is button 3 currently held?", you have to track that yourself with your own variables.

  4. No higher-level events: Pygame gives you MOUSEBUTTONDOWN and MOUSEMOTION separately. If you want drag, drop, or focus events, you build the state machine yourself.

GlitchyGames solves all of these: events are dispatched through named on_*_event() methods (no if/elif chains), event managers track state (buttons, axes, focus), and synthesized events (drag, drop, chord) are generated automatically.

Raw events and polling

A scene that defines process_event(event) gets every raw pygame.event.Event instead of the on_*_event() handlers. For smooth movement, poll the frame's input snapshot (current_input().key_pressed(...), see Gameplay Recording and Replay) while still receiving on_key_down_event() for discrete key actions; polling pygame directly (pygame.key.get_pressed()) works live but cannot be replayed. Never call pygame.event.get() yourself: the engine is the queue's only reader.

But this architecture creates a new problem: what happens to events that nobody handles?

The unhandled event problem#

GlitchyGames gives every on_*_event() a default stub (the *EventStubs classes in src/glitchygames/events/input_event_interfaces.py and system_event_interfaces.py; Scene inherits AllEventStubs). If your scene doesn't override on_joy_axis_motion_event, the stub catches the event instead of silently dropping it and calls unhandled_event() (src/glitchygames/events/base.py). This is powerful for debugging — you can see exactly which events your game isn't handling.

But stubs run on every occurrence of their event. A joystick thumbstick drifting slightly generates JOYAXISMOTION events continuously, even when nothing is listening, so unhandled_event() must be cheap and quiet after the first one.

Example: one frame at 60 FPS#

Imagine a player is moving the mouse while a joystick is connected. In a single frame (~16ms), pygame might deliver these events:

Event Source Has a handler?
MOUSEMOTION Mouse moved 3px Yes — scene implements on_mouse_motion_event
JOYAXISMOTION Joystick thumbstick drift No — scene doesn't handle joystick
JOYAXISMOTION Same thumbstick, new value No — still unhandled
JOYAXISMOTION Same thumbstick, new value No — still unhandled

The handled MOUSEMOTION flows through the proxy chain and reaches the scene's real handler.

But the three JOYAXISMOTION events hit the stub, which calls unhandled_event().

One warning per type, then silence#

unhandled_event() reads the game's options and:

  • with no_unhandled_events (--no-unhandled-events, and every test) raises UnhandledEventError;
  • with debug_events (--debug-events), logs Unhandled Event: <name> <event> at WARNING the first time it sees each event type (a module-level set of seen types), and nothing after;
  • otherwise does nothing.

Frame 1:  (type already seen, nothing logged)
Frame 1:  (type already seen, nothing logged)

(1 log call total, then 0 per frame)

Separately, GameEngine.process_unimplemented_event handles events that no process_*_event method dispatched (types with no EVENT_HANDLERS entry, or a handler that returned False): it counts each type in GameEngine.unhandled_events (count, first-seen time, attribute names) and the engine logs that table at teardown.

Why HashableEvent#

Raw pygame.event.Event objects are not hashable, so they cannot be dictionary keys, set members or functools.cache arguments, and they are mutable. HashableEvent is hashable by its content and immutable, and its fields (pos, button, key, etc.) read as attributes. Events are also serializable: to_json() / from_json() (below), pickling, structured logging. Raw pygame.event.Event objects support none of these.

The synthesized events — drag, drop, chord, focus — carry their extra context as extra handler arguments, never by changing the event: the mouse drag handler receives both the current MOUSEMOTION event and the MOUSEBUTTONDOWN trigger that started the drag, and the keyboard chord handlers receive the held keys' KEYDOWN events as keys: tuple[KeyEvent, ...].

Typed event classes#

HashableEvent(type, **fields) builds the class its type maps to in EVENT_CLASSES (src/glitchygames/events/base.py, exported by glitchygames.events), so a MOUSEMOTION is a MouseMotionEvent however it was built (the engine's dispatch, HashableEvent.from_pygame(pygame_event), tests, games). The classes only declare the fields pygame-ce gives their types, for the type checker; they store, hash, compare, pickle and serialize exactly as HashableEvent. Equality is by type and fields, never by Python class. Custom and field-less types (QUIT, MENUEVENT, USEREVENT, the APP_* events) stay HashableEvent, whose undeclared fields read as Any.

Immutability and the cached hash#

An event never changes after construction. Item and attribute assignment, deletion, update, clear, pop, popitem, setdefault and |= raise TypeError; event.with_fields(**changes) (or event | changes) returns a changed copy of the same class (its type cannot change). event.dict is a read-only view. The hash is computed on the first hash(event) and kept in a slot outside the fields, so it never shows in iteration, len(), dict(event), the pickled state or to_json(); a pickled or with_fields copy computes its own. Field values should be immutable too: a list inside a game event is hashed by its contents once.

JSON#

event.to_json() returns {"type": <number>, "attributes": {...}}, the attributes encoded as a recording encodes an event's (glitchygames.recording.json_safe_value: tuples as lists; lists, dicts, bytes and non-finite floats tagged), except that a window is written as None, as a replay serves it. HashableEvent.from_json(record) reverses it, and also reads a recording's event records (a recorded window reference becomes None). Recordings themselves still store the raw pygame events (recording.event_to_record); their format is unchanged.

Joystick vs Controller: Two Input Subsystems#

GlitchyGames supports two distinct SDL input subsystems for gamepads: Joystick (low-level) and Controller (high-level). They coexist because they serve different needs, and some devices only work with one or the other.

Why two subsystems?#

Joystick (pygame.joystick) Controller (pygame._sdl2.controller)
Abstraction level Raw hardware — axes, buttons, hats, balls are numbered Semantic — A/B/X/Y, D-pad, triggers, thumbsticks by name
Device support Everything SDL recognizes as a joystick Only devices with an SDL GameController mapping
Button/axis identity Button 0, Axis 2 (meaning varies by device) CONTROLLER_BUTTON_A, CONTROLLER_AXIS_LEFTX (consistent)
Mapping None — raw hardware indices SDL's built-in GameController DB maps hardware to semantic names
Hotplug ID device_index (unstable) + instance_id (stable) the same: added by device_index, everything after by instance_id
Touchpad support No Yes (CONTROLLERTOUCHPAD* events)
Remapping events No Yes (CONTROLLERDEVICEREMAPPED)

A mapped gamepad is one SDL device read on both: the joystick layer and the controller layer, with one instance id, and SDL sends every press on both (JOYBUTTONDOWN and CONTROLLERBUTTONDOWN). The engine runs both managers and hands each press to the game once (below).

One device, one event layer#

InputDevices (src/glitchygames/input/input_devices.py, whose docstring holds the rules) is the engine's list of the devices a game sees, by instance id: GameEngine.input_devices, or self.input_devices in a scene. Each InputDevice has the devices door's descriptor (name, GUID, device index, instance id, counts), a joystick layer (always) and a controller layer (a mapped pad only); both read the frame's input snapshot, so polling either always works and replays exactly. event_layer is the layer whose events reach on_*_event handlers: the controller layer when the device has one, else the joystick layer. The engine drops the other layer's input events (handled, never unhandled), so a mapped pad's press arrives once, as on_controller_button_down_event, and any other device's as on_joy_button_down_event. Device events (added, removed, remapped) always pass; a scene is also told of each device with on_input_device_added(device=...) / on_input_device_removed(device=...) once the registry has it (a mapped pad, which arrives and leaves on both layers, once each way).

--input-mode filters what the game sees: auto (the default) every device as above, joystick every device on its joystick layer only (SDL blocks controller events), controller mapped pads only (other devices are hidden and their events dropped). ActionMap binds the same families: auto binds a controller_button to both. The joystick demo (src/demos/joystick-demo/src/joystick_demo/__init__.py) lists every device with its event layer's live inputs.

for device in self.input_devices:
    layer = device.controller if device.controller is not None else device.joystick
    print(device.name, layer.axes, layer.buttons)

Disabling joystick events disables controller events

SDL's GameController API is built on top of the joystick subsystem. If you call pygame.event.set_blocked() on joystick event types (JOYAXISMOTION, JOYBUTTONDOWN, etc.), SDL will also stop delivering the corresponding controller events (CONTROLLERAXISMOTION, CONTROLLERBUTTONDOWN, etc.). If you need controllers but not raw joysticks, leave the joystick events unblocked: the engine already drops a mapped pad's joystick-layer input events (One device, one event layer, above).

JoystickEventManager architecture#

Unlike other event managers, JoystickEventManager manages multiple proxy objects — one per connected joystick. The outer manager is still a singleton, but it maintains a self.joysticks dict keyed by instance_id, and routes each event to the correct proxy based on the event's joystick identity.

This is necessary because:

  1. Multiple devices: There can be 1–N joysticks connected simultaneously. Other managers (Mouse, Keyboard) handle a single global device.
  2. Per-device state: Each joystick has its own axis values, button states, hat positions, and trackball deltas. These must be tracked independently.
  3. ID instability: SDL's device_index can change when devices are added/removed. The manager uses instance_id (stable for the lifetime of a connection) as the dict key instead.

Cached properties#

The proxy reads several joystick properties once, at init (some hardware answers metadata queries slowly):

  • _name — joystick name string
  • _guid — hardware GUID
  • _init — initialization status
  • _power_level — battery level (if supported)
  • _numaxes, _numballs, _numbuttons, _numhats — capability counts

The proxy exposes get_name(), get_numaxes(), etc., matching the pygame.joystick.Joystick API. get_name() asks the joystick first and returns the cached _name only when that fails; the others return the cached values.

ControllerEventManager architecture#

ControllerEventManager follows the same multi-proxy pattern as Joystick — one ControllerEventProxy per connected controller, keyed by instance id in self.controllers (the id every controller event carries). The key differences:

  1. SDL GameController API: Uses pygame._sdl2.controller instead of pygame.joystick. This provides semantic button/axis names (A, B, X, Y, left trigger, etc.) instead of raw hardware indices.
  2. Fixed axis/button sets: Controller proxies define AXIS and BUTTONS class variables with the standard SDL GameController constants. The proxy still allows dynamic growth for non-standard buttons.
  3. Touchpad events: Controllers support CONTROLLERTOUCHPADDOWN, CONTROLLERTOUCHPADMOTION, and CONTROLLERTOUCHPADUP — events that have no joystick equivalent.
  4. Remapping: CONTROLLERDEVICEREMAPPED fires when SDL updates a controller's button mapping at runtime. No joystick equivalent.
  5. No caching needed: The SDL GameController API doesn't suffer from the slow flash-read problem that raw joysticks have, so controller names and metadata are queried directly.
  6. Hotplug: CONTROLLERDEVICEADDED names a device index; the manager opens the controller there and keys it by the instance id it opens with, so a replugged controller (a new instance id at the same index) is found by its events. CONTROLLERDEVICEREMAPPED and CONTROLLERDEVICEREMOVED carry the instance id.

Joystick state tracking#

Each JoystickEventProxy maintains cached arrays for every input on its device. They start from the frame's input snapshot (current_input(), so live play and a replay start alike; a device hot-plugged this frame starts zeroed), never from the hardware, and events update them. To poll a device, prefer InputDevices (above), which reads the snapshot.

Button state#

Buttons are tracked as a list[bool]. The list grows dynamically if a device reports a button index beyond the initially detected count.

# Proxy state update on JOYBUTTONDOWN

self._buttons[event.button] = True

# Proxy state update on JOYBUTTONUP
self._buttons[event.button] = False

Axis state#

Axes are tracked as a list[float]. Each axis value ranges from -1.0 to 1.0.

stateDiagram-v2

    Idle --> Updated : JOYAXISMOTION
    Updated --> Updated : JOYAXISMOTION

    state Idle {
        [*] : _axes[i] = 0.0

    state Updated {
        [*] : _axes[i] = event.value, range -1.0 to 1.0
    }
# Proxy state update on JOYAXISMOTION
self._axes[event.axis] = event.value

Hat state#

Hats (D-pads) are tracked as a list[tuple[int, int]]. Each value is an (x, y) pair where x and y are -1, 0, or 1.

    state Centered {
        [*] : _hats[i] = 0, 0

Trackball state#

Trackballs are tracked as a list[tuple[int, int]] (starting at (0, 0): they are not in the snapshot) storing the relative motion of the last event.

# Proxy state update on JOYBALLMOTION
self._balls[event.ball] = event.rel  # (dx, dy) tuple

Unhandled Event Safety Net#

When an event has no handler, the stub system catches it. The behavior is configurable: silent, logged, or error-raising (used in tests).

Both settings come from the command line, through the scene's options (GameEngine.OPTIONS): no_unhandled_events is the --no-unhandled-events argument (Game Options), and debug_events is the --debug-events flag (Diagnostics Options, off by default: a run opts in to the warnings). A replay keeps its own --debug-events, never the recording's (REPLAY_LOCAL_OPTIONS).

flowchart TD
    EVENT["Event arrives at\non_*_event() stub"] --> UH["unhandled_event()"]
    UH --> CHECK_STRICT{"options#91;'no_unhandled_events'#93;?<br/>#40;the --no-unhandled-events argument#41;"}
    CHECK_STRICT -->|"Yes"| RAISE["Raise UnhandledEventError\n(used in test suite)"]
    CHECK_STRICT -->|"No"| CHECK_DEBUG{"options#91;'debug_events'#93;?<br/>#40;the --debug-events flag, off by default#41;"}
    CHECK_DEBUG -->|"Yes"| LOG_W["Log WARNING\nfirst occurrence of the type only"]
    CHECK_DEBUG -->|"No"| SILENT["Nothing"]

Events no process_*_event method handled go to GameEngine.process_unimplemented_event, which counts them by type in GameEngine.unhandled_events; _shutdown logs the table at teardown (unhandled_event_report(): e.g. JOYDEVICEADDED (1541) x1, first at 0.3 s, attributes: device_index, guid).

Scene transitions in Bitmappy#

The active_scene pointer determines which scene receives all events. A scene asks for a switch by setting self.next_scene; after the frame, the SceneManager calls switch_to_scene(next_scene), which:

  1. Calls cleanup() on the current scene
  2. Calls setup() on the next scene
  3. Updates active_scene to point to the next scene
  4. All subsequent events flow to the new scene

A next_scene of None means no switch is pending; it never ends the game. A scene that names itself is treated the same way and reset to None (a scene referring to itself is a reference cycle, which only the cycle collector frees). A scene ends the run with self.scene_manager.quit(), which posts a QUIT event.

EVENT_HANDLERS Dict Construction#

The EVENT_HANDLERS dict (a class attribute of GameEngine) is built once during GameEngine.__init__() by initialize_event_handlers(). This pre-computation avoids per-event if/elif chains, giving O(1) dispatch.

How it's built#

At startup, initialize_event_handlers() iterates over each event category's list of pygame event type constants and maps every one to the corresponding process_*_event method:

Event list pygame types Handler
AUDIO_EVENTS AUDIODEVICEADDED, AUDIODEVICEREMOVED process_audio_event
CONTROLLER_EVENTS CONTROLLERAXISMOTION, CONTROLLERBUTTONDOWN, ... process_controller_event
KEYBOARD_EVENTS KEYDOWN, KEYUP process_keyboard_event
MOUSE_EVENTS MOUSEMOTION, MOUSEBUTTONDOWN, MOUSEBUTTONUP, MOUSEWHEEL process_mouse_event
JOYSTICK_EVENTS JOYAXISMOTION, JOYBUTTONDOWN, JOYBUTTONUP, ... process_joystick_event
WINDOW_EVENTS WINDOWCLOSE, WINDOWRESIZED, WINDOWMOVED, ... process_window_event (WINDOWDISPLAYCHANGED, WINDOWICCPROFCHANGED unhandled)
DROP_EVENTS DROPBEGIN, DROPFILE, DROPTEXT, DROPCOMPLETE process_drop_event
TOUCH_EVENTS FINGERDOWN, FINGERMOTION, FINGERUP, MULTIGESTURE process_touch_event (MULTIGESTURE unhandled)
GAME_EVENTS every other supported type, plus FPSEVENT, GAMEEVENT, MENUEVENT (QUIT, ACTIVEEVENT, USEREVENT, ...) process_game_event
APP_EVENTS APP_TERMINATING, APP_LOWMEMORY, ... process_app_event
MIDI_EVENTS MIDIIN, MIDIOUT process_midi_event
TEXT_EVENTS TEXTEDITING, TEXTINPUT process_text_event (both passed to the scene manager)

The result is a flat dict mapping every pygame event type integer to its category's handler method; each process_*_event then picks the manager method for the type and returns whether it handled it.
