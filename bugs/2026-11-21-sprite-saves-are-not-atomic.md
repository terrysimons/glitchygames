# Sprite Saves Are Not Atomic

- **Description**: Four writers of a user's own file write it in place: they truncate the file, then write it. If Ctrl-C, a crash, a kill or a power cut stops the write part way, the file is left truncated, and the earlier version is gone with it. Found by the sweep of every file write in `src/` and `scripts/` for bugs/2026-11-20-ledger-row-writes-are-not-atomic.md (2026-11-21), by reading the code. Not observed or reproduced.
  - `AnimatedSprite.save` (`src/glitchygames/sprites/animated.py:2025`, `Path.write_text`): Bitmappy saves an animated sprite through it (`animated_canvas.py`, `canvas_interfaces.py`).
  - `BitmappySprite.save`, the static save (`src/glitchygames/sprites/bitmappy_sprite.py:465`): `open('wb')`, then `tomli_w.dump`, so a stop inside the dump leaves part of the TOML.
  - Bitmappy's TOML saved from a PNG (`src/apps/bitmappy/src/bitmappy/file_io.py:388`, `Path.write_text`).
  - Bitmappy's error-handling config (`src/apps/bitmappy/src/bitmappy/controllers/error_handling.py:376`, `open('w')` then `json.dump`): a truncated config no longer loads.
- **Status**: Fixed (2026-11-21, branch fix/sprite-saves-are-atomic)
- **Priority**: High. Each one destroys a person's work or settings, and no copy is kept.
- **Root Cause**: a file the user keeps is written in place instead of whole or nothing.
- **Test gap**: no test stops a save part way. The save tests write only to completion, and nothing holds a save to the whole-or-nothing rule.
- **Already whole or nothing** (the pattern to follow):
  - `sprites/saved_sprites.py` (the AI console's `/sprite`) and Bitmappy's AI save (`ai_manager.py`, which wraps `canvas_sprite.save` in `write_aside_then_replace`).
  - `state/manager.py` (saves), `audio/disk_cache.py`, `audio/offline.py`, `replay/rebuild.py`, `replay/tools/sound_tools.py` and `ai_console.py`.
  - Since 2026-11-21, the replay ledgers.
- **Fix**:
  - The four writers, plus the sprite catalog's export (`sprites/catalog.export_sprite_texts`, the same defect, found by the guard below), write through `output_files.write_text_whole`, which syncs the partial file before the replace. The static save renders with `tomli_w.dumps` and the config with `json.dumps`, so each is one text. `saved_sprites.save_sprite` moved from `write_aside_then_replace` to `write_text_whole`, so the AI console's `/sprite` save is synced too.
  - Regression tests, each seen to fail first (the earlier file came back cut to 10 characters): a save stopped part way with `tests/interrupted_writes.py`'s `cut_writes_short` leaves the earlier file unchanged and no partial file behind. `TestAnimatedSpriteSaveIsWholeOrNothing` (`tests/sprites/test_animated_sprite.py`), `TestStaticSaveIsWholeOrNothing` (`tests/sprites/test_sprite_bitmappy.py`), `TestExportIsWholeOrNothing` (`tests/sprites/test_sprite_catalog.py`), `TestPngConversionSaveIsWholeOrNothing` (`src/apps/bitmappy/tests/test_bitmappy_file_io.py`) and `TestConfigSaveIsWholeOrNothing` (`src/apps/bitmappy/tests/test_bitmappy_multi_controller_error_handling.py`).
  - Guards for the class: `tests/sprites/test_sprite_save_source_guard.py` fails on any in-place write in a `glitchygames.sprites` module, and `src/apps/bitmappy/tests/test_bitmappy_save_source_guard.py` on any in Bitmappy beyond its allowance (the AI manager's temporary TOML file for a request, one call). Both scan every module of their package, using `tests/ast_scanning.writing_calls`, and each was seen to fail on a planted in-place save.
  - Line ends (the owner's decision, 2026-11-22): a save writes the OS's line ends (CRLF on Windows, LF elsewhere), so a person on Windows can open a sprite in their usual text editor and change it, as on macOS and Linux. Readers take either and hold the text with LF line ends, so what is in memory is the same whichever OS saved the file. `write_text_whole` keeps text mode's default translation; nothing pins LF. Before this branch, `AnimatedSprite.save` (`write_text`) already wrote CRLF on Windows, and the static save (`'wb'`) wrote LF there: the static save now writes CRLF on Windows too. Tests: CRLF and LF sprite files load to the same frames in `AnimatedSprite`, `BitmappySprite` and the catalog; a save writes `os.linesep` line ends (`test_the_file_has_the_os_line_ends`, and `test_a_crlf_file_saves_again_with_the_os_line_ends` for both sprite classes); a CRLF file loaded, saved and loaded again has the same text in memory (`test_a_crlf_file_saved_and_loaded_again_has_the_same_text`, `..._has_the_same_sprite`). The readers needed no change: tomllib turns CRLF into LF inside multi-line strings, and the sprite text is built from the parsed values (a CRLF file's `to_text()` has no CR). On macOS the save tests pass either way; each failed with a CRLF translation planted, and CircleCI's Windows job runs them for real.
- **Related**:
  - `state/manager.DiskSaveManager._atomic_write` is a third copy of `output_files.write_aside_then_replace` (`NamedTemporaryFile` plus `replace`). Fold it into the shared helper, keeping its `newline='\n'` (a save has the same bytes on every OS).
  - `tests/test_ledger_write_source_guard.py` does not scan `scripts/measure_on_raspberry_pi.py`, because engine tests never reach `scripts/`. That script writes no ledger itself, but its local `tarfile.extractall` of a Pi's row files is not whole or nothing: a cut extraction leaves a truncated, untracked row that readers skip and the next push overwrites. Low risk.
  - Lower risk, also found by the sweep:
    - `testing/frame_fingerprints.py`'s records append (a test diagnostic, with no guard against a cut last line);
    - `api/client.py` and `api/sprite_requests.py` (new AI sprite files, written in place);
    - `tracing.py`'s recording file, which is written over the whole run by design.
- **Known remaining gap** (the class is partly covered, not closed): whole-or-nothing holds against a stop (Ctrl-C, a crash, a kill), but not fully against a power loss.
  - Only `output_files.write_text_whole` syncs its file before the replace. Its callers are the replay ledgers (`recording_metrics.write_ledger_file`, and `append_ledger_rows`, which syncs its own append) and, since this record's fix, the sprite saves: `AnimatedSprite.save`, `BitmappySprite`'s static save, `catalog.export_sprite_texts`, `saved_sprites.save_sprite`, and Bitmappy's PNG conversion and error-handling config.
  - No writer syncs the directory after the replace. On some file systems, a power cut just after it can still show the old file.
  - `write_aside_then_replace` stays unsynced, so after a power loss its destination can come back empty or partial on some file systems. Its callers are `ai_console.py` (the console's question history), `audio/offline.py` (two renders), `replay/rebuild.py` (the restart handoff), `replay/tools/sound_tools.py` and `replay/driver.py` (a bookmarked copy), plus Bitmappy's `ai_manager.py`.
  - `state/manager.DiskSaveManager._atomic_write` and `audio/disk_cache.py` also replace without syncing.
  - The replay outputs and bookmarks can be made again. The user's saves still unsynced (the state saves and Bitmappy's AI save) should use `write_text_whole` or a synced equivalent.
