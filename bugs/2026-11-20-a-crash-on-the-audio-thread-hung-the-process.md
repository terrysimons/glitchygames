# A Crash on the Audio Thread Hung the Process Forever Instead of Ending It

- **Description**: A pre-push `compare-drivers` run (the native cocoa + coreaudio driver, 16 workers, `fix/docs-play-stale-browser-site`, 2026-11-19/20) hung for 3 h 46 min. One pytest-xdist worker spun at about 95% CPU and the other 15 sat idle. A macOS `sample` of the worker showed two threads. The main thread was in `pygame.mixer.init` → `Mix_OpenAudioDevice` → `COREAUDIO_OpenDevice`, waiting forever on `SDL_SemWait` for the audio thread to say the device was open. SDL's AudioQueue thread was in `audioqueue_thread` → `AudioQueueNewOutput` → `_dispatch_workloop_activate`, where it took a fatal signal. Then `faulthandler_fatal_error` handed the signal on to `pygame_parachute`, whose `_pg_quit` → `_Py_Dealloc` spun with no GIL held. The worker's last recorded test was `tests/audio/test_audio_engine.py::TestDiagnosticsAndSnapshot::test_a_soloed_bus_is_in_the_snapshot` (passed, 23:52). The hung test itself is unknown: xdist schedules by load, and faulthandler's traceback went to the worker's stderr, which the pre-push output did not keep.
- **Status**: Fixed (2026-11-20, on `fix/native-audio-open-hang`)
- **Priority**: High. A push or test run stalls for hours with no failure and no test named. A game that hits the same crash freezes with a spinning core until it is force-quit.
- **Root Cause**: pygame-ce installs a handler, its "parachute" (`pygame_parachute`, `src_c/base.c`), when `pygame` is first imported. It goes on each of SIGSEGV, SIGBUS, SIGFPE and SIGQUIT still at its default. The handler calls `pygame.quit()` (`_pg_quit`) before `Py_FatalError`, and that touches Python objects. On a thread that does not hold the GIL (every SDL thread), it never returns, so the process never ends. The test harness imports pygame (`tests/harness.py`) before pytest enables its faulthandler, so faulthandler chained to the parachute after printing its traceback. Every game imports pygame before the engine (the import order ruff gives), so a game had the parachute too. Reproduced: crash a thread that has released the GIL after `import pygame`. With the parachute it hangs; with faulthandler enabled after pygame it prints, then hangs. With faulthandler enabled before pygame, or the fatal signals reset after it, the process dies at once (exit -11). The crash itself is in Apple's audio code under a parallel native run. It is the same family as plans/future-work.md's CoreAudio flake (`AudioQueueStart -66681`, 2026-11-11), which errored instead of crashing. It is not fixable here: the fix makes it a fast, named failure.
- **Test gap**: nothing crashed a process to see that it ended. The suite had no stand-in for a crash off the main thread, and no limit made a hung test show where it waited.
- **Solution**: `report_fatal_signals_with_faulthandler` (`glitchygames/engine/game_engine.py`) puts each fatal signal back to its default, then enables faulthandler. That drops the parachute, so a crash prints every thread's traceback and ends the process. `GameEngine.__init__` calls it before `pygame.init()` opens the audio device. The test harness calls it at import, before pytest enables its own faulthandler, which then changes only where the traceback is written. It does nothing when faulthandler is already enabled (whoever enabled it chose), or off the main thread (Python sets handlers there only). It still drops the parachute when there is no stderr to write to (a windowed build). pytest's `faulthandler_timeout = 600` (`pyproject.toml`) prints every thread's traceback for a test still running after ten minutes, so a hang that is not a crash names its test. In the browser it is harmless: in Pyodide 314 the signal and faulthandler calls succeed, Pyodide cannot start threads, and a WebAssembly crash is a trap, not a signal (checked by hand in the browser build's Pyodide, 2026-11-20).
- **Tests**: `tests/engine/test_engine_fatal_signals.py`:
  - a game (pygame imported first, then an engine built) and a process that loaded the test harness each die of a crash on a thread without the GIL, with faulthandler's line. Both hung until killed at 60 s before the fix;
  - the fatal signals are pygame's four;
  - an enabled faulthandler is left alone (proven by a planted defect);
  - each signal goes back to its default before faulthandler is enabled;
  - no usable stderr still drops the parachute;
  - another thread changes nothing.

  `tests/test_suite_collection.py`: the ten-minute `faulthandler_timeout` is set.
- **Siblings** (processes that import pygame and open a device without the engine or the harness, 2026-11-20): uncovered, all by-hand tools, none run by the suite or CI.
  - `scripts/audio_glitch_probe.py` and `scripts/measure_sound_memory.py` open the real audio device;
  - `scripts/animation_demo.py`, `scripts/animation_scene_demo.py`, `scripts/audit_hitboxes.py` and `scripts/experiments/quickstart*.py` open a display;
  - `tests/audio/channel_fade_probe.py`, a test's child process, opens the mixer on SDL's disk driver, not CoreAudio.

  Each would keep the parachute; a call to `report_fatal_signals_with_faulthandler()` after its imports would cover it.
- **Limitation**: a program that enables faulthandler itself after `import pygame` keeps the parachute behind it. The engine cannot tell, since a C handler is invisible to `signal.getsignal`.
