# The Trace Reader Copied the Rest of Its Buffer for Every Line

- **Description**: CircleCI's Linux test jobs on #215's successors (#220, #221, #224, #225) stopped at the test memory guard (1752-1763 MiB of 1750) in `tests/test_every_recording_replays_inside_an_inner_game.py`, the Zombies Ain't My Neighbors pair (bugs/2026-11-18-sprite-frames-held-a-tuple-per-pixel.md has the sprite half). Profiled with memray in a 2 GB arm64 Ubuntu container (CI's limits and pytest arguments), that one test allocated 17.45 GB in total for a 266 MB peak; 3.53 GB of it was `TraceReader._next_line` (`src/glitchygames/tracing.py`). The churn left Python's small-object arenas fragmented: repeating the test in one process kept 10-30 MiB more memory after each run while the bytes in use stayed flat.
- **Status**: Fixed (2026-11-19, on `fix/sprite-frame-memory`)
- **Priority**: High (every replay of every game pays it, not only tests: the reader serves `--replay-trace`, demos, ghosts, audits and every golden check)
- **Root Cause**: `_next_line` took each line with `line, newline, rest = self._pending.partition(b'\n')` and kept `rest`, a new copy of every byte after the line. The reader decompresses 64 KiB of the file at a time; one chunk of the zombies neighborhood golden unpacks to about 1 MiB of 1.4 KiB lines, so each of its ~700 lines copied what was left: about 350 MB copied per chunk, quadratic in the lines a chunk holds. Its loop also searched the whole buffer for a newline again after every chunk, so a line longer than a chunk was searched once per chunk.
- **Test gap**: the reader's tests checked what it returns (frames, partial lines, damaged lines, streaming from a small chunk), never what reading costs; only the memory guard saw it, as a test that happened to replay a big recording several times.
- **Solution**: the unread text starts at an offset (`_pending_start`): taking a line moves the offset and slices out only the line. The unread tail is copied once, when the next chunk is appended, and the newline search resumes where the tail ended.
- **Measured** (memray, the zombies pair case on `fix/sprite-frame-memory` 7541b2a7, `--no-cov`): `_next_line` 3.53 GB allocated before, 181 MB after; the test's total 17.45 GB before, 13.94 GB after.
- **Tests**: `tests/test_tracing.py` `TestTraceReader.test_taking_a_line_never_copies_the_rest_of_the_buffer`: 40,000 frames read from one chunk (3.3 MB decompressed) with the extra traced memory under half the decompressed size. Before the fix the extra memory was the whole of it (3,314,904 bytes for 3,312,255), as each line held the buffer and a copy of its rest at once.
- **Siblings** (a sweep of `src/`, `scripts/`, `services/ai-service/src/` and `tests/` for line-peeling buffers, 2026-11-19): none. The other stream readers read a whole message (`ai_link.py`'s session, `tests/test_ai_link.py`) or fill a `bytearray` to an exact count (`replay/tools/compare.py` `receive_exactly`, and the copy of it in `tests/replay/tools/test_compare_trace.py`).
- **Found with it, not fixed here**: in the same test, `Tile.run_frames` copies each tile's whole render target every frame to hash it (`pygame.image.tobytes`, 9.18 GB of the 17.45): a cost in time, not in memory kept (1.4 MB blocks freed at once, outside the small-object arenas). Compiling sounds (`audio/render.py` `_table_samples`, `_curve_shape`) allocated about 1.07 GB.
