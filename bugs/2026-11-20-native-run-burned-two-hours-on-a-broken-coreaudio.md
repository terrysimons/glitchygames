# The Native Comparison Run Burned Two Hours on a Broken CoreAudio, Then Blamed the Change's Frames

- **Description**: Twice on 2026-11-20 macOS CoreAudio misbehaved under `nox -s compare-drivers`' native (cocoa) run, and the gate handled it badly both times. (1) On the docs-play-fix push, `pygame.mixer.init` deadlocked (`Mix_OpenAudioDevice`) and the run hung until it was killed by hand: no per-test time limit existed. (2) On the perf push (`glitchygames-perf-hot-paths/build/push-perf-coreaudio-66681.log`) every mixer start failed: the cocoa run ended `236 failed, 30177 passed, 11 skipped, 5 xfailed, 123 errors in 7201.86s (2:00:01)` (a healthy native run takes 341 s; the 7200 s is the two-hour cap), `pygame.error: CoreAudio error (AudioQueueStart): -66681` in 268 failures by the overnight ledger's count (322 `E` lines in the log). The session then reported "235 test(s) presented different frames", but every one was really "no audio": Paddle Slap's bounce sound `None`, and `InnerGameChannelsError` because `reserve_inner_game_channels` returns nothing without a mixer. Afterwards eight parallel mixer inits all succeeded in 0.22 s, so the fault was transient.
- **Status**: Fixed (2026-11-20, branch `fix/pre-push-robustness`): the gate's handling. The machine fault itself is not.
- **Priority**: Medium (two lost pushes; two hours once)
- **Root Cause**: Of the gate's handling: nothing checked the machine's audio before a two-hour run, nothing limited one test's time (so a hung call stalled the whole run), and the report counted every test whose frames or outcome differed between dummy and cocoa as a frame difference, whatever the reason. Of the machine fault: unverified. The coreaudiod log beside the failed run (`build/coreaudiod-errors-0620-0830.log`, 32 lines) holds only microphone DSP-graph parameter errors (`Failed to set param: gmco on dsp graph: builtin_microphone_general`), nothing about `AudioQueueStart` or -66681, so it does not explain it. The overnight session saw both faults come and go without a reboot.
- **Test gap**: No test or gate step exercised the native audio device before the long run, none bounded a test's duration on the native run, and the classification of differing tests knew only "frames differ".
- **Solution**: (a) Before any run, compare-drivers opens and closes one mixer (44100 Hz, signed 16-bit, stereo, 512 buffer) in a child process with a 30 s limit, for each configuration whose audio driver is native; an error or hang stops the session at once, naming the error and saying it is the machine's audio (retry; `sudo killall coreaudiod`). (b) Differing tests whose native failure text carries `CoreAudio error` or `mixer not initialized` are reported as "audio failed in N test(s)", never as frame differences. (c) The native run only gets `--timeout=120 --timeout-method=thread` plus `faulthandler_timeout=110` (pytest-timeout, a dev dependency). Not in CI or a plain pytest.
- **Known limits**: The thread method ends the worker with `os._exit` (xdist reports the crash and replaces the worker), so a hung test's children, in sessions of their own, may outlive the worker: the child-process guard's fixture teardown never runs. Not tested. A no-audio failure with no message (an assertion on a missing sound) is not labelled as audio; the probe is what catches that case. A fault that starts after the probe passes still costs a run, though bounded by 120 s per test.
- **The class, and its invariant**: a gate step depends on a machine service (the audio device) that can fail without the change being at fault, and reports its failure as the change's. The invariant: such a dependency is probed before the long run, a test's time is bounded, and a failure naming the service is labelled with it. `tests/test_native_audio_health.py` (probe success, error and hang; labelling from a junit fixture with CoreAudio failures; the probe runs before any test run) and `tests/test_driver_frame_matrix.py::TestNativeRunTimeLimit` (only the native run carries the limit; a real pytest with xdist fails a hung test).
- **Sweep**: Covered: compare-drivers' cocoa run, the only place the native audio device runs in a gate. Uncovered: other native audio users (Windows' wasapi probe is the same code but unexercised here); the in-process native run of plain `pytest` (`tests/driver_comparison.py`) has no probe and no time limit; CI uses dummy audio.
- **Tests**: `tests/test_native_audio_health.py` (28), `tests/test_driver_frame_matrix.py::TestNativeRunTimeLimit`; before the fix the native-run command had no limit (4 tests failed with the timeout arguments removed).
