# The Native Comparison Run Burned Two Hours on a Broken CoreAudio, Then Blamed the Change's Frames

- **Description**: Twice on 2026-11-20 macOS CoreAudio misbehaved under `nox -s compare-drivers`' native (cocoa) run, and the gate handled it badly both times. (1) On the docs-play-fix push, `pygame.mixer.init` hung and the run stayed hung until it was killed by hand: no per-test time limit existed. The cause is verified (the Zombies session's macOS `sample` of pid 64737, taken before anything was stopped; #252, `bugs/2026-11-20-a-crash-on-the-audio-thread-hung-the-process.md`, on its branch): the main thread sat in `pygame.mixer.init` -> `Mix_OpenAudioDevice` -> `COREAUDIO_OpenDevice` -> `SDL_SemWait` forever; SDL's audio thread crashed (fatal signal in `AudioQueueNewOutput`) while `pygame.mixer.init` waited for it, and pygame-ce's parachute handler (`_sigtramp` -> `faulthandler_fatal_error` -> `pygame_parachute` -> `_pg_quit` -> `_Py_Dealloc`) spun forever on that GIL-free thread, so the semaphore was never posted. (2) On the perf push (`glitchygames-perf-hot-paths/build/push-perf-coreaudio-66681.log`; that worktree was removed on 2026-11-24 and its logs archived to `.ledger/archive/worktree-leftovers-2026-11-24/glitchygames-perf-hot-paths/build/`, on the owner's Mac) every mixer start failed: the cocoa run ended `236 failed, 30177 passed, 11 skipped, 5 xfailed, 123 errors in 7201.86s (2:00:01)` (a healthy native run takes 341 s; the 7200 s is the two-hour cap), `pygame.error: CoreAudio error (AudioQueueStart): -66681` in 268 failures by the overnight ledger's count (322 `E` lines in the log). The session then reported "235 test(s) presented different frames", but every one was really "no audio": Paddle Slap's bounce sound `None`, and `InnerGameChannelsError` because `reserve_inner_game_channels` returns nothing without a mixer. Afterwards eight parallel mixer inits all succeeded in 0.22 s, so the fault was transient.
- **Status**: Fixed (2026-11-20, branch `fix/pre-push-robustness`): the gate's handling. The hang's cause is fixed by #252 (a crash on the audio thread now fails at once); this branch's per-test limit (360 s since 2026-11-22, first 120 s) still catches a hang that is not a crash. The cause of the second fault (`-66681`) is not known.
- **Priority**: Medium (two lost pushes; two hours once)
- **Root Cause**: Of the gate's handling: nothing checked the machine's audio before a two-hour run, nothing limited one test's time (so a hung call stalled the whole run), and the report counted every test whose frames or outcome differed between dummy and cocoa as a frame difference, whatever the reason. Of the first fault (the hang): the crash and the parachute handler described above. Of the second fault (`-66681`): unverified. The coreaudiod log beside the failed run (`build/coreaudiod-errors-0620-0830.log`, 32 lines, archived beside it) holds only microphone DSP-graph parameter errors (`Failed to set param: gmco on dsp graph: builtin_microphone_general`), nothing about `AudioQueueStart` or -66681, so it does not explain it. The overnight session saw both faults come and go without a reboot.
- **Test gap**: No test or gate step exercised the native audio device before the long run, none bounded a test's duration on the native run, and the classification of differing tests knew only "frames differ".
- **Solution**: (a) Before any run, compare-drivers opens and closes one mixer (44100 Hz, signed 16-bit, stereo, 512 buffer) in a child process with a 30 s limit, for each configuration whose audio driver is native; an error or hang stops the session at once, naming the error and saying it is the machine's audio (retry; `sudo killall coreaudiod`). (b) Differing tests whose native failure text carries `CoreAudio error` or `mixer not initialized` are reported as "audio failed in N test(s)", never as frame differences. (c) The native run only gets `--timeout=360 --timeout-method=thread` plus `faulthandler_timeout=350` (pytest-timeout, a dev dependency). Not in CI or a plain pytest. The limit was 120 s; on 2026-11-22 it became 360 s, longer than any test's own wait on a child (300 s at most, checked by `tests/test_per_test_limit.py`), after it ended a test waiting on its Mr. Muncher replay at a load average of 176 (`bugs/2026-11-20-process-stop-tests-failed-under-load.md`, second sighting).
- **Known limits**: The thread method ends the worker with `os._exit` (xdist reports the crash and replaces the worker), so no fixture teardown runs. That left the test's children running with no parent (reproduced 2026-11-22: a child waited on through `run_command` was still running, parent 1, after the run had exited). Fixed 2026-11-22 (`fix/native-limit-stops-children`): `tests/per_test_limit.py` times the thread method itself and, when the limit fires, kills and reaps every child the harness's guard recorded (each running child, every process in a group one led, their descendants) before pytest-timeout ends the worker; `tests/test_per_test_limit.py` runs the reproduction (it failed with the plugin off) and checks that a test ending in time has its timer cancelled. Its line naming what it stopped was lost on #287's Linux job 5171 (2026-11-23): written to `sys.__stderr__`, which is descriptor 2, it landed in the test's fd capture and vanished whenever the test was reported before pytest-timeout's dump read that capture (0 of 6 plain runs showed it in a Linux container; macOS hid it locally only because the shell's `PYTEST_ADDOPTS` held `-s`). It now writes to the run's original standard error (`tests/original_standard_error.py`, shared with the memory guard), and the inner runs drop `PYTEST_ADDOPTS` as pytester does; `test_the_line_naming_the_stopped_children_survives_the_tests_own_capture` forces that order (6 of 6 failures before the fix). Still not stopped: a child the guard does not record (one started before the test's function-scoped fixtures, or without `subprocess`). A no-audio failure with no message (an assertion on a missing sound) is not labelled as audio; the probe is what catches that case. A fault that starts after the probe passes still costs a run, though bounded by the per-test limit.
- **The class, and its invariant**: a gate step depends on a machine service (the audio device) that can fail without the change being at fault, and reports its failure as the change's. The invariant: such a dependency is probed before the long run, a test's time is bounded, and a failure naming the service is labelled with it. `tests/test_native_audio_health.py` (probe success, error and hang; labelling from a junit fixture with CoreAudio failures; the probe runs before any test run) and `tests/test_driver_frame_matrix.py::TestNativeRunTimeLimit` (only the native run carries the limit; a real pytest with xdist fails a hung test).
- **Sweep**: Covered: compare-drivers' cocoa run, the only place the native audio device runs in a gate. Uncovered: other native audio users (Windows' wasapi probe is the same code but unexercised here); the in-process native run of plain `pytest` (`tests/driver_comparison.py`) has no probe and no time limit; CI uses dummy audio.
- **Tests**: `tests/test_native_audio_health.py` (28), `tests/test_driver_frame_matrix.py::TestNativeRunTimeLimit`; before the fix the native-run command had no limit (4 tests failed with the timeout arguments removed).
