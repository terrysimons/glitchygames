# The Free Space Was Read From the Wrong Column

- **Description**: Three checks read the free disk space as a field of `df`'s table, counted from the start of the line: setup.sh's model download (`ansible/roles/ai_package/templates/setup.sh.j2`, `df -k "$models" | tail -1 | awk '{print $4}'`), Ansible's Mac model download (`ansible/roles/ai_models/tasks/main.yml`, `df -k` then `stdout_lines[-1].split()[3]`) and the llama.cpp build (`ansible/roles/llama_cpp/tasks/main.yml`, `df -m` the same way). The table names the filesystem first, so a name holding a space moves every field one to the right, and the fourth field is then Used, not Available. Reproduced on GNU df 9.7 in `ubuntu:26.04` and `debian:trixie` (privileged containers, a tmpfs mounted as `my models`): the true free space was 65536 KiB, and setup.sh read 0. Two ways wrong: an empty disk read as full, so "not enough disk space" at every run and the models never downloaded (the service never starts); a nearly full one read as its used size, so the download went ahead and filled it. Two more faults in the same read: an empty reading (df failing) counted as 0 KiB, the same permanent refusal, and a word in its place stopped setup.sh outright (dash: `Illegal number: -`, exit 2) with an exit code the script never documents (0 or 1).
- **Status**: Fixed (2026-11-20, on `fix/free-disk-space-field-parsing`)
- **Priority**: Medium (only a filesystem whose name has a space: an SMB network home such as `//user@server/Home Dirs`, an sshfs or rclone mount; not seen on the owner's machines, but for that user the service never starts, or a download fills the disk)
- **Root Cause**: a value cut from a line that also holds a name the program doesn't control, by its position from the start. The #237 sweep for the checksum bug saw setup.sh's line and left it ("not seen on the owner's machines"; `bugs/2026-11-19-model-checksum-kept-the-escape-mark.md`, Siblings).
- **Test gap**: no test ran a free-space check against any `df` but the host's own, whose filesystem names (`/dev/disk3s5`) hold no space. The two Ansible checks had no test at all.
- **Solution**: every check runs one command per platform that prints the number alone, `ai_free_space_command` in `ansible/group_vars/linux.yml` and `macos.yml`: on Linux GNU `df -k --output=avail --` (the "Avail" header, then the number; GNU df 9.7 and uutils both have it); on a Mac, whose df has no `--output`, osascript's JavaScript asks Foundation's file manager (`NSFileSystemFreeSize`, the `f_bavail` statfs(2) gives; `ai_free_space_program`), printing nothing for a path it can't read. setup.sh's `free_kib_of` (`platform_functions.sh.j2`) and both Ansible tasks run that command and read its output's last line. A reading that isn't digits is logged with what the command printed and said (setup.sh: "free space unknown (read '…'; error '…'); downloading FILE anyway"; Ansible: "Free disk space unknown: osascript printed "…" and said "…"; downloading anyway"), so a disk that really fills shows why, and the download or build goes ahead (the owner's call): the check only saves work that would fail anyway (curl stops on a full disk, and the `.part` resumes on the next run), so a broken reading must not stop the service for good.
- **Tests**: `tests/test_ansible_ai_service.py`:
  - `test_setup_reads_the_free_space_whatever_the_filesystem_is_called[room-my models]` and `[full-my models]`: RED before the fix (64 GiB free read as "not enough disk space" for every model; a full disk downloaded); the `/dev/mmcblk0p2` cases passed before and after. `test_setup_downloads_anyway_when_the_free_space_cannot_be_read`: RED before (refused at every run).
  - `test_free_kib_of_reads_what_the_filesystem_reports[Linux|Darwin]` and `test_ansible_measures_the_free_space_as_the_number_alone[ai_models|llama_cpp-Linux|Darwin]`: each platform's real tool where the host has it (GNU df on Linux, osascript on a Mac), against `os.statvfs` of a folder named with a space. The `ai_models` Mac case was RED against the old task (df's whole table, not a number).
  - `test_ansible_refuses_only_work_that_wont_fit[...]`: both Ansible checks, for room, room under df's header, a full disk, no output and a word.
  - GNU df on a Mac host is `GNU_DF_STUB`, built from GNU's documented output (https://www.gnu.org/software/coreutils/manual/html_node/df-invocation.html) and compared with GNU df 9.7 in `ubuntu:26.04` and `debian:trixie` on the `my models` tmpfs.
- **Guard for the class**: `tests/test_command_field_readers_guard.py` scans the shell and Ansible files under `ansible/`, `scripts/` and `services/` for every field read from a command's output (awk `$N`, `cut -f`, `read -r` into two names, Jinja `.split()[N]`) and holds each to a reviewed list saying why no name can move it; a new or changed reader fails until it is reviewed. It finds the three old df reads and the checksum's old form when planted.
- **Siblings** (that scan, 2026-11-20): 29 readers, all reviewed and listed. One can shift in principle: `scripts/raspberry_pi_llama_cpp/benchmark_llama_cpp.sh`'s `major_faults` reads `/proc/PID/stat` field 12, after the process name, which can hold a space; the process is llama-server, which that script starts, and the number is a diagnostic only. Not changed.
