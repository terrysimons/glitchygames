# The Model Checksum Kept the Tool's Escape Mark

- **Description**: setup.sh (`ansible/roles/ai_package/templates/setup.sh.j2`) checks each downloaded model with `sha256_of` (`ansible/roles/ai_service/templates/platform_functions.sh.j2`), which ran `sha256sum "$1" | cut -d ' ' -f 1` on Linux and `shasum -a 256 "$1" | cut -d ' ' -f 1` on a Mac. Given a file name holding a backslash or a line break, both tools escape the name and start the line with a backslash (`\73cb…  /home/a\\b/…`), so the cut field was `\` plus the hash. Every downloaded model then had "the wrong SHA-256" and was discarded, at every run, for a user whose home (or XDG data folder) has such a name: the service never started for them. CircleCI's Linux job (4020) showed it as `test_every_ai_unit_is_told_the_user_root_however_odd_the_home` failing, once it ran in the cimg/python:3.15.2 container.
- **Status**: Fixed (2026-11-19, on `feature/ai-service-raspberry-pi`)
- **Priority**: Medium (only a home or XDG folder with a backslash or line break in its name, but for that user the service never starts, and nothing says why beyond the discarded downloads)
- **Root Cause**: the hash was cut from a line that also names the file, and the tools' output for an unusual name is not "hash, two spaces, name". GNU coreutils documents it (https://www.gnu.org/software/coreutils/manual/html_node/md5sum-invocation.html): a backslash, newline or carriage return in the name is escaped with a backslash and the line starts with a backslash. uutils coreutils (Ubuntu 26.04's `sha256sum`, in cimg/python:3.15.2) prints the same, and so does the Mac's Perl `shasum` (6.02 on the owner's Mac, 6.04 in the container; it leaves a carriage return unescaped). The Mac's `/sbin/sha256sum` does not escape, which is why the Linux branch passed when the tests ran on a Mac.
- **Test gap**: the setup tests ran only on the Mac, where the Linux rendering called the Mac's `/sbin/sha256sum` (BSD, no escaping) instead of GNU's; the Mac rendering's `shasum` was never given an unusual name, since only the Linux setup test uses an odd home.
- **Solution**: `sha256_of` reads the file on standard input on both platforms (`sha256sum < "$1"`, `shasum -a 256 < "$1"`), so the line names no file (`-`), and keeps `cut -d ' ' -f 1`.
- **Tests**: `tests/test_ansible_ai_service.py`:
  - `test_sha256_of_gives_the_bare_hash_whatever_the_file_is_called[...]`, both systems, for a folder named with a backslash, a newline and a carriage return. Before the fix 5 of the 6 failed (`\5a39…` for `5a39…`); the Mac's carriage-return case passed, as `shasum` leaves that unescaped.
  - `test_every_ai_unit_is_told_the_user_root_however_odd_the_home[4]` and `[1]` failed on the Mac too before the fix, once the Linux rendering had a GNU-behaving `sha256sum`.
  - The GNU behaviour on a Mac host is a stub built from GNU's documented contract (`GNU_SHA256SUM_STUB`, put in a Linux `ServiceHome`'s tools only when the host isn't Linux; a Linux host uses its real tool). Its output was compared byte for byte with uutils `sha256sum` in cimg/python:3.15.2 for a backslash, a newline, a carriage return and standard input. The fixed functions, rendered for each system, were run in that container with the real `sha256sum` and `shasum` on a file under `/tmp/a\b/` and printed the bare hash.
- **Siblings** (a sweep of `ansible/` templates and tasks for tool output that names a file and is cut into fields, 2026-11-19):
  - `deb-postrm.sh.j2` `bounded_du "$folder" | awk '{ print $1 }'`: the size comes first, so a backslash is harmless (du prints names unescaped). A folder name with a line break splits du's line, and awk then prints the size and the name's second half on two lines (checked with uutils du 0.10.0 in the container): only the removal notice's text is broken, nothing is decided from it. Fixed in the review's follow-up (2026-11-19): the size is taken from du's first line only (`awk 'NR == 1 { print $1 }'`), tested by `test_postrm_gives_one_size_for_a_folder_whose_name_holds_a_line_break` (RED before: the size read `4.0K` plus the name's second half on a line of its own). A real home can't hold a line break (a passwd entry is one line), so only the test's injected root of homes reaches it today.
  - `setup.sh.j2` `df -k "$models" | tail -1 | awk '{print $4}'`: no file name from the user before the field, but a filesystem name with a space (a Mac's autofs `map auto_home`) would move the field; not seen on the owner's machines. Not changed.
  - `deb-prerm.sh.j2` `loginctl list-users --no-legend | awk '{ print $2 }'`: user names hold no spaces. `platform_functions.sh.j2`'s core ranking (`cut -d ' ' -f 2`) and `/proc/meminfo` reads: no names. None affected.
