# The Mac Package's Settings Name The Builder's Runtime

- **Description**: Every model agent's settings template in the Mac `.pkg` (`share/agents/<label>.env.template`) names llama-server by the builder's own absolute path, for example `AI_LLAMA_SERVER='/Users/<builder>/Library/Application Support/GlitchyGames/AI/runtime/llama.cpp-b12167-<hash>/bin/llama-server'`. It should be the home placeholder (`__GLITCHYGAMES_HOME__/Library/...`). setup.sh fills in only the placeholder, so on any Mac but the builder's, every model agent points into a home that does not exist there, and `run-llama-server.sh` refuses to start. The other paths in the same file (models, keys) do carry the placeholder
- **Status**: Fixed (2026-11-19, branch `feature/ai-service-raspberry-pi`, commit "Ansible: the Mac package names the player's runtime through runtime/current; the .deb's maintainer"; the owner's decision of 2026-11-19)
- **Priority**: High for any second Mac (the package's models never start there); none on the builder's own Mac, where the path is right by coincidence
- **Root Cause**: `ansible/roles/ai_package/tasks/macos.yml` renders the settings inside a block whose `vars` set `ai_home` to the placeholder and `llama_cpp_install_directory` to `{{ ai_program_root }}/runtime/<name>`. The llama_cpp role sets `llama_cpp_install_directory` with `set_fact`, and a fact outranks a block's variables (Ansible's precedence: block vars 16, set_facts 19, include params 21), so the block's value is ignored. `ai_home` works, as it is a group variable, which a block's variables do outrank. Reproduced with ansible-core 2.22.0: a localhost playbook running role ai_package after a `set_fact` of the install directory renders the builder's path. Present since the package's settings were first staged, before the Linux work
- **Test gap**: nothing tested what the `.pkg`'s settings hold; the tests that rendered settings set variables directly (`ansible_variables(overrides=...)`), which ignores Ansible's precedence, so a value Ansible would never use looked right
- **Solution**: macos.yml passes `ai_home` (the placeholder) and `llama_cpp_install_directory` as the include's variables on `include_tasks: settings.yml`, as linux.yml does: include variables outrank facts. The plists keep the block, as they name nothing the llama_cpp role sets. The settings name the runtime through `runtime/current`, a link the `.pkg` now ships (staged by the shared `stage.yml`, as the `.deb` does), so an upgrade that renames the runtime folder leaves every player's settings right. The `.pkg`'s staged files change only by that link and the `AI_LLAMA_SERVER` line of each model's settings template, which now reads `__GLITCHYGAMES_HOME__/Library/Application Support/GlitchyGames/AI/runtime/current/bin/llama-server`
- **Tests**: `tests/test_ansible_ai_service.py::test_the_mac_package_settings_name_the_players_runtime` (a strict xfail until the fix, now an ordinary test: it walks the role's tasks with Ansible's precedence, `PackageStaging`, and fails on the builder's path, as it did against the old macos.yml); `test_a_mac_upgrade_that_renames_the_runtime_keeps_the_settings_valid` (the player's filled-in setting resolves to the old build, then to the renamed one, unchanged); `test_the_mac_package_stage_is_unchanged_but_for_the_runtime_link`. `test_the_linux_settings_name_both_roots_by_their_placeholders` covers the Linux side. Proved in real ansible-core 2.22.0 with a throwaway build into a temporary folder: the staged list gains only `runtime/current` and each model's settings change only on `AI_LLAMA_SERVER`
