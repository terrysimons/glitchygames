# Browser Frames Juddered at 120 Hz

- **Description**: In the browser, Zombies Ain't My Neighbors' title screen (the blinking P1-P4 slots) hitched. Measured in Chrome on a 120 Hz MacBook Pro display (`scripts/measure_browser_frames.py --headed`), every frame cost under 2 ms of a 16.7 ms budget and every animation frame arrived on time (8.3 ms apart, the longest 9.4 ms), yet `TickPacer` ran frames after one tick and then three (8 and 25 ms) instead of every second tick: in one 16-second run 38 of each among 961 frames, in another 46 and 101. Headless Chrome (60 Hz ticks) never juddered. Text was not the cause: every image is rendered once in `setup()`, and drawing the five text sprites costs 0.35-0.4 ms a frame.
- **Status**: Fixed (2026-11-20, on `fix/browser-pacer-judder`)
- **Priority**: High (every browser game on a 120 Hz or 240 Hz display: ProMotion Macs, many phones and gaming monitors)
- **Root Cause**: `TickPacer.should_run_frame` (`src/glitchygames/host.py`) added each tick's interval to an accumulator and ran a frame once it held the frame period less half a tick (16.664 - 4.17 = 12.50 ms), then paid one period. Two ticks never equal the default period exactly (60.01 FPS, `timing.DEFAULT_TARGET_FPS`; a display a little off 120 Hz), so the leftover after each frame drifts a few microseconds a frame. Once it drifted to about 4 ms, one tick later the accumulator held 11.9-12.5 ms: on the threshold, so each tick's jitter (7.6-9.4 ms) decided the frame. A tick that tipped it over ran a frame after one tick, the leftover went to -4.1 ms, and the next frame needed three ticks. The recorded pacing decisions (accumulator before and after each tick) show exactly this.
- **Test gap**: the pacer's tests used an exact 60 FPS period (never the 60.01 default) and perfectly even ticks at exactly 120 Hz, so the leftover never drifted and no tick jittered.
- **Solution**: a period within `WHOLE_TICK_TOLERANCE` (2%) of a whole number of measured ticks runs a frame on exactly every that many ticks (`whole_ticks_per_frame`), counting a late tick as the ticks its interval spans and starting again from each frame, so a missed animation frame delays only its own frame and nothing ever runs early to make up time. The frames then follow the display (59.9 FPS for 60.01 at 119.75 Hz); `dt` is measured, so game time stays right. Other periods (60 FPS on 144 Hz) keep the accumulator. Both counts run on every tick, so the measured tick settling in the first ticks (a switch between the two) loses nothing.
- **Measured** (headed Chrome, 120 Hz, the title for 16 s): before, frames after 1/2/3 ticks 38/883/38 (run 4) and 46/754/101 (run 1); after, two runs of 960 and 959 frames all after two ticks, the longest frame interval 17.7 ms. A run before the fix was also clean once (the leftover had not drifted to the threshold), so the tests are the proof.
- **Tests**: `tests/test_host.py` `TestTickPacer`: `test_jittered_drifting_one_hundred_twenty_hertz_runs_a_frame_every_second_tick` (a minute of 119.5-120.5 Hz ticks each up to 0.8 ms off, a fresh seed each run plus the saved seed 547288780; before the fix 125 frames after one tick and 101 after three of 3,611), `test_a_missed_animation_frame_delays_one_frame_with_no_catch_up_frame` (before: the 25 ms frame was followed by one 8 ms later), `test_recorded_chrome_animation_frames_run_a_frame_every_second_tick` (the recorded ticks, `tests/fixtures/pacing/chrome-120-hz-animation-frames.json`: it passed before the fix too, since a new pacer's leftover drifts too slowly on 16 seconds to reach the threshold; it holds the pacing to the real ticks' shape), and `TestWholeTicksPerFrame`. 2,000 seeds of the jittered test pass; 60 and 240 Hz run every one and four ticks, 90, 144 and 165 Hz still average 60 FPS.
- **Siblings** (cadences decided by an accumulator against a fixed threshold, swept in `src/glitchygames`, 2026-11-20): the engine's own pacing (`timing.py`) sleeps to deadlines and has no display ticks (not this class). The replay viewer (`replay/viewer.py`) snaps ticks within `TICK_SNAP_WINDOW_SECONDS` of its 60 Hz control tick to exactly one period, which covers its own sleep timer; but in the browser (`run_watched_replay_async`) its ticks are animation frames, and at 120 Hz no tick is near 1/60 s, so none snaps: uncovered, not measured (plans/future-work.md).
- **Found with it, not fixed here**: the title's five text sprites are `dirty=2`, so every frame alpha-blends about 66,600 pixels and updates five rects though only the blink changes (0.35-0.4 ms a frame in the browser). Making them `dirty=1` would trip `SceneManager._update_display`, which updates the whole screen when a frame has no dirty rects (plans/future-work.md).
