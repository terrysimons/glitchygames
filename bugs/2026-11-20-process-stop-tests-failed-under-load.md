# Three Process-Stop Tests Failed Under Heavy Load

- **Description**: One full local `pytest` run (macOS, the owner's machine, 2026-11-20 20:23, `fix/assert-replacement-engine`) failed three tests that start real child processes and check how they stop; all three pass on their own (4 cases in 8.5 s), and four other full runs that day passed them. The failing run took 12 min 19 s against the usual 8½–9 min, with the load average at 25 over 15 minutes (other sessions were running suites on the same machine).
  - `tests/test_driver_comparison.py::TestStoppingTheNativeRun::test_a_stopped_native_run_leaves_no_process_its_tests_started`: `AssertionError: the stand-in test left its child running` (`process_exists` true for the stand-in's child after the stop).
  - `tests/test_reproduce_orphaned_test_processes.py::TestTrials::test_sigint_to_the_runs_group_leaves_nothing`: `result.left_running` held the stand-in's `python -c "import time; time.sleep(120)"` child (under a `glitchygames-orphans-…` temporary folder) after SIGINT to the run's group.
  - `tests/replay/tools/test_command_crash_boundary.py::test_a_signal_stops_and_reaps_the_commands_child_and_exits_with_its_code[2]`: `subprocess.TimeoutExpired` from `running.wait(timeout=COMMAND_DEADLINE_SECONDS)` (60 s): the `record-trace` command did not exit within the deadline after SIGINT. The SIGTERM case (`[15]`) passed in the same run.
  A rerun of the whole suite right after (load rising to 46) passed all three, so the failure is intermittent, not load alone. No orphan was found running afterwards (the stand-in children sleep 120 s and had exited).
- **Status**: Open (triage under way; seen twice, the second time on 2026-11-21)
- **Priority**: Medium (the first two guard BUGS.md #275, orphaned test processes: if a child really escapes the stop under load, the guard's bug is back where load is highest, CircleCI's split Linux jobs and the Pis)
- **Root Cause**: Not established. Two explanations, needing opposite fixes:
  - late, not leaked: the child dies moments after the check, which looks once, too soon under load; the fix is a bounded wait for the child's exit, which is what the stop promises;
  - leaked: under load a child escapes `process.stop_command` (a suspect: a child forked after the group signal was sent); the fix is in the stop, with a regression test that drives that race.
  For the third, the log does not say whether the 60 s went on the game starting (its pid file) or on the command stopping. The third's `child_left_running` failures are explained under "The third test: root cause" below (SIGINT proven, SIGTERM a candidate); its 60 s hang in the first sighting is not.
- **Related fix checked** (dev-glitchygames-97, 2026-11-20, against `fix/killpg-misses-forked-process`, which SIGKILLs a group member that missed the SIGINT; the guard skips unreaped zombies): not a duplicate.
  - `test_a_stopped_native_run_leaves_no_process_its_tests_started`: not covered. The stand-in's child is in a session of its own, outside the group, and stops only if the inner test's SIGINT cleanup runs; a SIGKILL of a member that missed the SIGINT still skips that cleanup.
  - `test_sigint_to_the_runs_group_leaves_nothing`: partly covered (a dying worker, by that branch's `end_the_run` change and the guard skipping zombies), but not a stand-in child left in its own session after a missed SIGINT.
  - `test_a_signal_stops_and_reaps_the_commands_child_and_exits_with_its_code[2]`: not covered; it is the command's own SIGINT teardown.
  - An option 97 recorded, not built, for this triage to decide: send the gentle signal once more to members still in the group before the SIGKILL, at the risk of interrupting a cleanup already running.
  The triage starts after the current set of work clears (the owner's freeze on new work, 2026-11-20).
- **Test gap**: each test checks a process outcome once against an instant or a fixed deadline, so a slow machine and a real leak fail the same way and can't be told apart from the failure.
- **Triage plan**: reproduce under deliberate load (the three tests in a loop, ~50 runs, beside a CPU load on every core) to measure the rate; on a "left running" failure, keep polling the child for a few seconds and log when it dies and its parent; split the third test's 60 s into start-up and stop. Then fix by what that shows, and give every test that checks a process or signal outcome against a fixed instant one shared bounded wait. The plan goes to the coordinating session for its cross-check before coding.

- **Proposal: passive capture** (for the owner to decide when the freeze lifts): an opt-in environment variable that loads the probe (`scripts/process_stop_probe/`) in every process of an ordinary full-suite run and keeps its event log only when the run fails, so the next time this happens on its own the log names who sent each signal and when, at no extra run.
  - Where it would be on: the pre-push gate's `test-random` and `compare-drivers`, and CI's split Linux and Windows jobs (the probe is POSIX-only, so Windows would skip it); not plain `pytest` by default.
  - What it needs: the variable sets `PYTHONPATH` to the probe's folder and `PROCESS_STOP_PROBE_LOG` to a file in the run's results; the gate deletes the file after a passing run and keeps it beside the failure (CI as an artifact). A check that the probe loaded in a nested run, as the reproducer has, so an empty log can't pass for evidence.
  - Cost to measure first: the probe adds a JSON line and a stack walk (six frames) per `os.kill`/`os.killpg` and per signal received, plus a start and an exit line per Python process; the suite starts thousands of processes. Measure a whole-suite run with and without it (wall time, and the log's size), then decide whether to keep it on always, only in the pre-push gate, or only on demand.

- **The third test: root cause** (2026-11-22; it had refused five pushes by then: `[2]` for three sessions, `[2]` and `[15]` for one, `[15]` for this one):
  - `[2]` (SIGINT), proven: the command exits with its game killed but not reaped. `record-trace` runs the game through `process.run_command`, which is `subprocess.run`. On KeyboardInterrupt, `subprocess.run` waits 0.25 s, sends SIGKILL and re-raises; `Popen.__exit__` then skips its wait on purpose for a KeyboardInterrupt (CPython's bpo-25942, read in 3.15.1's `subprocess.py`). The crash boundary turns the interrupt into exit 130, and the game is left as a zombie for launchd to reap after the command has gone. A probe (an `atexit` hook in the command that lists its own children with `ps`) found the game unreaped (`Z`) at the command's exit in 50 of 50 SIGINT runs, at load 9 and at load 94; at the SIGTERM path's exit it found no child, 0 of 50 (`exit_on_signal`'s SystemExit takes `__exit__`'s waiting branch). The test passes only when launchd reaps the orphan before the test's `os.kill(pid, 0)`. It did every time with CPU burners (load 94) or an orphan storm (load 51), so how slow launchd gets in a full suite was not reproduced, but the contract the test states (the child is reaped before the command ends) is broken on every SIGINT, at any load.
  - `[15]` (SIGTERM), not reproduced (55 of 55 clean), and a candidate only: the failure exited 143, so `exit_on_signal` ran. The one path to SystemExit(143) that leaves the game unreaped is the signal arriving while the command is still inside `Popen.__init__`, after the fork (the read of the exec-status pipe, the pipe closes), or between `Popen` returning and `subprocess.run`'s `try`. There, nothing kills or waits for the child, which keeps running until the test's `stop_command` kills its group. Hitting that window needs the command to be starved from the fork until after the game has started Python and written its pid file, which a load of 176 on 16 cores makes possible. Not proven.
  - Not 97's PR #263 (`stop_command` SIGKILLs a group member that macOS's `killpg` missed): that is the test's cleanup, after the check. It is neither cause, and it doesn't fix either.
  - The defect class: a launcher whose interrupt path returns without stopping and reaping its child. Every `run_command` caller has it on Ctrl-C, since all the engine's child launches go through it (`replay/tools/children.py`, `replay/audit.py`, `replay/rebuild.py`, `verify.py`, `measure.py`, `sound_cache_tools.py` and others). `run_command_stopped_at_timeout` reaps on any interrupt, but keeps the window inside `Popen.__init__`.
  - Test gap: the end-to-end test checks the outcome once, from outside, after the command has gone, so a broken reap passes whenever launchd is quick. Nothing tests the launcher's interrupt path in process, where an unreaped child is visible (`os.waitpid(pid, os.WNOHANG)` succeeds instead of raising `ChildProcessError`).
  - Options, for the owner to choose:
    - recommended: one launcher that owns its child's whole life. `run_command` becomes `Popen` plus a wait inside `try`/`except BaseException`, which stops and reaps (`stop_and_reap`: SIGTERM, then the grace period, then SIGKILL and a wait), sharing that path with `run_command_stopped_at_timeout` instead of mirroring it. SIGINT and the terminating signals are deferred while `Popen` is created (Python-level handlers that record a signal and raise it again once the child is inside the `try`; exec resets them to the default in the child), which closes the `[15]` window. A gentle stop also lets the game close its recording, which SIGKILL does not. Tests, proven RED on main: an interrupt while waiting leaves the child reaped before the launcher returns; a signal during the child's creation leaves it stopped and reaped; the end-to-end test unchanged.
    - narrower: handle KeyboardInterrupt in `record-trace`'s path only. That fixes the test that fails and leaves every other launch with the bug.
    - not recommended: make the test wait, bounded, for the child to disappear. That would hide the broken contract.
